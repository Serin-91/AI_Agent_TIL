
# 관심사 분리(SoC)와 레이어드 아키텍처

## 1. 관심사 분리 (Separation of Concerns)

프로그램을 역할과 책임에 따라 분리하는 설계 원칙.

- HTTP 처리, 업무 규칙, 데이터 접근 책임 분리
- 유지보수성과 테스트 편의성 향상
- 기능 변경 시 다른 코드에 미치는 영향 최소화

## 2. 레이어드 아키텍처

관심사 분리를 계층 구조로 적용하는 방식이다. FastAPI에서 강제하는 구조는 아니다.

| Layer | Responsibility |
|---|---|
| Router | HTTP 요청·응답 및 API 경로 관리 |
| Service | 비즈니스 로직과 작업 흐름 관리 |
| Repository | 데이터 CRUD 및 저장소 접근 |

### 처리 흐름

```text
Request
   ↓
Router
   ↓
Service
   ↓
Repository
   ↓
Data Storage
```

결과는 `return`을 통해 역방향으로 전달된다.

```text
Repository → Service → Router → Response
```

## 3. Pydantic과 비즈니스 검증

| 구분 | 역할 | 예시 |
|---|---|---|
| Pydantic | 데이터 형식 및 필드 검증 | 타입, 필수 값, 길이 |
| Service | 업무 규칙 검증 | 존재 여부, 권한, 재고 |

필드 검증은 Pydantic의 `Field`로 선언할 수 있으며, 업무 규칙은 Service에서 처리한다.

## 4. 프로젝트 구조

```text
project/
├── main.py
├── routers/
│   └── post_router.py
├── services/
│   └── post_service.py
├── repositories/
│   └── post_repository.py
└── schemas/
    └── post.py
```

### 주요 모델

- `PostCreate`: 생성 요청 DTO (`title`, `content`)
- `PostDetailResponse`: 상세 응답 (`id`, `title`, `content`)
- `PostListResponse`: 목록 응답 (`id`, `title`)
- `Post`: 저장소에서 관리하는 게시글 객체

## 5. CRUD 처리

| Operation | Service | Repository |
|---|---|---|
| Create | 입력 검증 및 객체 생성 | ID 부여 및 저장 |
| Read All | 조회 결과 반환 | 전체 목록 조회 |
| Read One | 존재 여부 판단, 404 처리 | ID 기반 조회 |
| Update | 입력값 및 존재 여부 검증 | 데이터 수정 |
| Delete | 존재 여부 검증 | 데이터 삭제 |

- 생성 직후 `Post.id`는 `None`이며 저장 과정에서 ID를 부여한다.
- 단일 조회 결과가 `None`이면 Service에서 404 예외를 발생시킨다.

## 6. 실행 및 API 테스트

```bash
uv run fastapi dev main.py
```

Swagger UI: `http://127.0.0.1:8000/docs`

| HTTP Status | 의미 |
|---|---|
| 200 | 조회·수정 성공 |
| 201 | 생성 성공 |
| 204 | 삭제 성공 (응답 본문 없음) |
| 404 | 대상 리소스 없음 |
| 422 | 입력 데이터 검증 실패 |

실습에서는 메모리 기반 저장소를 사용하므로 서버 재시작 시 데이터가 초기화된다.

## 7. 핵심 정리

- **Router:** HTTP 통신
- **Service:** 업무 규칙과 처리 흐름
- **Repository:** 데이터 저장소 처리
- **SoC:** 책임 분리의 설계 원칙
- **Layered Architecture:** 책임을 계층으로 나누는 구조

계층별 역할을 분리하고 계층 사이의 인터페이스를 유지하면 API, 비즈니스 로직, 데이터 저장 방식의 변경에 더 유연하게 대응할 수 있다.
