# **Agent 그래프 구조도**

> **이 문서는 비교용 Agent(T3)의 구조도다. 최종 시스템은 T4로, Agent가 아닌 3칸 RAG(후보 15개 → LLM rerank 5개 → 답변, `gemini-3.5-flash-lite`)다** (EVALUATION.md 1절, 그림은 시각화 자료.pdf). T3는 과제의 "기본 RAG 대 Agent" 비교를 위해 T2에 판단 노드를 더한 것이고, 7절의 v2는 채택하지 않은 시도다.
> 

상태: 구현 완료 (2026-10-21, `src/rag/agent.py`, LangGraph). 2026-10-22: 검색 노드가 T2와 같은 rerank를 거치고 답변 프롬프트는 설정을 따른다(최종 T3는 `answer_v4`). 최종 체인 위의 T3 수치는 6절 끝(dev는 카드 014에서 처음 실행). 초안과 달라진 점은 6절, 시도했지만 채택하지 않은 v2는 7절

## **1. 설계 의도**

- 기본 RAG와 같은 답변 프롬프트(`prompts/answer_v1.md`)와 같은 답변 함수(`rag.generate_answer`, `map_citations`, `format_answer`), 같은 검색기(`retrieval.load_retriever`)를 쓴다. 차이는 아래 구조뿐이다(PLAN.md 3.3절).
- 기본 RAG가 LLM 1회로 하던 판단을 나눈다: 답할 질문인지(classify), 근거가 충분한지(grade), 인용이 맞는지(cite_check).
- 근거가 부족하면 질문을 고쳐 다시 검색한다(rewrite → retrieve, 최대 2회).

## **2. 그래프**

`Agent.graph.get_graph().draw_mermaid()`로 만든 구현 그래프다(점선은 조건 분기).

- classify: 질문 유형 4가지(document / needs_info / inappropriate / injection). needs_info·inappropriate는 grade를 건너뛴다(근거 충분성 판단 없이 바로 generate).
- grade: 누적 문맥으로 답할 수 있는지 판단. 부족하고 재검색이 2회 미만이면 rewrite → retrieve. 2회 다 쓰면 그대로 generate (보류는 답변 프롬프트가 고른다).
- generate: 기본 RAG의 답변 단계(`answer_v1`). cite_check: 인용 번호가 문맥 밖이거나 `answered`인데 인용이 없으면 generate를 1회 더 한다.

## **3. 노드**

| 노드 | 역할 | LLM | 출력 |
| --- | --- | --- | --- |
| classify | 질문 유형 4가지 중 하나 (`prompts/agent_classify_v1.md`) | 1회 | 유형, 이유 |
| retrieve | 기본 RAG와 같은 검색(`BaselineRAG.retrieve`: Hybrid 후보 15개 → LLM rerank로 5개, 2026-10-22부터). 결과를 누적 문맥에 더한다(중복 제거, 총 10개까지) | 0 (임베딩만) | 청크 목록 |
| grade | 누적 문맥으로 답할 수 있는지 판단 (`agent_grade_v1.md`). needs_info·inappropriate는 건너뜀 | 0–1회 | 충분 / 부족 + 부족한 점 |
| rewrite | 부족한 점을 바탕으로 새 검색어 (`agent_rewrite_v1.md`), 최대 2회 | 0–1회 | 검색어 |
| generate | 기본 RAG와 같은 답변 단계 (`answer_v1.md`): status, 답변, 인용 번호 | 1회 | status, answer, citations |
| cite_check | 인용 번호가 실제 문맥 안에 있는지, `answered`에 인용이 있는지 코드로 확인 | 0 | 통과 / 실패 (실패 시 generate 1회 재시도) |

## **4. 종료 조건**

- END는 cite_check 다음에만 도달한다. 최종 status 4가지(answered / abstained / clarify / refused)는 generate가 답변 프롬프트로 고른다.
- 재검색은 최대 2회, 인용 재시도는 최대 1회. 최악의 경우 LLM 호출은 8회(classify 1, grade 3, rewrite 2, generate 2)이고, 최종 체인(T3)은 검색마다 rerank 1회가 더해져 11회다. 실측 문항당 평균: 이전 체인 dev 3.16회, 최종 체인 dev 4.06회(`dev_008b_agent950`). 최대 검색 3회.

## **5. 측정 장치 (구현 전에 정함)**

- 첫 검색 문맥과 누적 문맥을 따로 `metrics.context_metrics`로 채점한다. Agent의 첫 검색은 같은 질문에 대한 기본 RAG의 검색과 같으므로 직접 비교한다.
- 답변이 재검색으로만 찾은 청크를 인용했는지 기록한다(재검색의 효과를 문항 단위로 확인).
- 노드마다 판단, 모델, 토큰, 시간을 `steps`에 남긴다.

## **6. 초안과 달라진 점**

- **refuse / clarify / abstain 노드를 만들지 않았다.** 이유: (1) 답변 프롬프트가 이미 `status`와 거절·되묻기·보류 문장을 쓰며, 그 문장이 문서 인용(일반 정보 안내)을 필요로 해서 검색을 거쳐야 한다. (2) 같은 프롬프트를 쓰기로 한 설계(PLAN.md 3.3절)를 지키기 위해 별도 프롬프트를 더하지 않았다. 대신 classify가 needs_info·inappropriate 질문의 grade·재검색을 건너뛰게 한다.
- **classify는 질문을 고쳐 쓰지 않는다.** 첫 검색이 기본 RAG의 검색과 같아야 직접 비교가 되기 때문이다(5절). 주입 문구는 답변 프롬프트의 규칙 4가 처리한다.
- **누적 문맥 상한 10개**를 추가했다(첫 검색 5 + 새 청크 최대 5). 재검색을 두 번 해도 답변 입력이 3배로 늘지 않게 하기 위해서다.
- 노드 구성을 바꾼 근거는 실패 분석(PROCESS.md 6절)의 "근거 부족" 25문항(검색 실패 7, 근거 일부 누락 13, 과잉 보류 5)을 재검색 노드가 겨냥하고, negative 6문항(NEG014 NEG025 NEG037 NEG039 NEG022 NEG023)은 공통 답변 단계가 다룬다는 판단이다.
- dev 결과(카드 008, 이전 체인): 점수 0.822 → 0.856, 순승 +3으로 오차 범위. 재검색은 9문항, 그중 3문항이 재검색으로만 찾은 청크를 인용했다.
- 최종 체인(T3 = T2 + 이 그래프) 결과. 세 세트 모두 Agent가 앞서지만 각각 오차 범위다.

## **4. Agent 설계 회고**

- **설계 순서가 거꾸로였다.** Agent는 이전 체인의 실패 분석(근거 부족 25문항)에 맞춰 재검색 중심으로 만들었다(카드 008). 그 뒤 청킹·rerank가 검색 문제를 거의 다 풀었다(dev page_hit@5 0.99). Agent가 겨냥한 실패가 사라진 셈이다. 다시 한다면 **검색 튜닝을 끝낸 체인에서 실패를 다시 나누고** 그 결과로 노드를 정한다.
- **판단을 만들고 쓰지 않은 노드가 있었다.** 분류 노드는 NEG013을 "정보 부족"으로 맞게 나눴지만, 그 결과를 근거 판단을 건너뛰는 데만 썼고 답변 단계에는 넘기지 않았다. 노드마다 "이 판단을 누가 읽는가"를 구조도에 적었다면 일찍 찾았을 것이다(v2에서 고쳤다).
- **수업의 표준 구조(23번 Agentic RAG)를 그대로 따르지 않은 부분은 데이터로 정했다.** 3회 검색 뒤 고정 문구로 보류하는 노드는 만들지 않았다. 근거 부족으로 끝난 4문항 중 2문항(ADD-HF06 부분 근거로 만점, NEG034 올바른 거절)을 잃기 때문이다.
- **그래도 Agent는 세 세트 모두에서 조금씩 앞섰다.** dev 0.939 대 0.928, 제공 test 0.911 대 0.883, 자작 0.927 대 0.902. 각각은 잡음 안이지만 방향이 세 번 같다. 비용 1.3~1.5배를 감수할 만한지는 이 크기의 평가로는 가를 수 없다.

## **5. 평가 설계 회고**

- **잘한 것**
    - 잡음을 먼저 쟀다(같은 설정을 다시 돌리면 90문항 중 14개가 바뀜). 그래서 +0.03 같은 차이를 개선이라고 쓰지 않았다.
    - 실험 카드에 판단 기준을 결과보다 먼저 적었다. 사용자가 기준과 다르게 채택한 경우에도 "기준 미달, 사용자 채택"으로 남아 나중에 근거를 따라갈 수 있다.
    - 검색 평가(LLM 없음)와 답변 평가를 나눠, "못 찾음"과 "찾고도 틀림"을 구분했다.
- **아쉬운 것**
    - 채점 모델(3.6-flash)이 T2·T3의 답변 모델과 같다. 자기 답을 후하게 볼 수 있다(EVALUATION 7절).
    - 첫 자작 골든셋 20문항이 너무 쉬워 T2가 만점을 받았고, 다시 썼다.
    - 제공 test를 두 번 봤다(가격 때문에 최종 모델을 바꿈). 비용 비교를 test 전에 끝냈어야 했다.
    - dev 90문항으로는 순승 9문항 미만의 차이를 가를 수 없었다. 결정 대부분이 "잡음 안, 사용자 판단"으로 끝난 이유다.

## **6. 진행 방식 회고**

- **동결 규칙이 재현성을 지켰다.** 한 번 실행에 쓴 프롬프트·골든셋·설정은 고치지 않고 새 판을 만들었다(답변 프롬프트 v1~v5). 그래서 T1~T4 결과가 지금 코드로 그대로 재현된다.
- **작은 확인을 건너뛴 사고가 두 번 있었다.** rerank 프롬프트의 `{k}`가 치환되지 않은 채 돌았고(macOS `sed`), test 전에 인덱스가 없는 줄 몰랐다. 둘 다 "1문항만 먼저 돌려 보기"로 막을 수 있었다(PROCESS 10절).
- **여러 세션이 같은 브랜치에서 일했다.** 마지막 날 다른 세션이 최종 정리를 하는 동안 Agent v2를 같은 폴더에서 고치면 서로 덮어쓸 위험이 있어, 별도 작업 폴더(git worktree)에서 하고 합쳤다.
- **LLM 호출 장부**를 끝까지 유지했다(누적 7,775회, PROCESS 11절 장부). 실험마다 비용을 같이 볼 수 있었다.

## **7. 다시 한다면**

1. 기준 RAG를 돌린 직후 **답변 모델·rerank처럼 효과가 큰 축을 먼저** 정하고, 그 체인에서 실패를 다시 나눈 뒤 Agent를 설계한다.
2. **채점 모델을 답변 후보와 다른 모델로** 처음부터 고정한다.
3. 자작 골든셋은 기준 시스템으로 몇 문항을 돌려 **난이도부터 확인**한다(결과를 문항 선택에 쓰지 않는 범위에서).
4. **가격 같은 결정 조건을 test 전에** 모두 정한다.
5. 모든 배치 실행 전에 **`-limit 1`로 한 문항을 먼저** 돌린다.
