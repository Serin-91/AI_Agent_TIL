# 1. 🔗 Self Join

## 무엇인가?

**Self Join은 하나의 테이블을 자기 자신과 JOIN하는 방식**이다.

실제로 테이블이 두 개 존재하는 것은 아니고, 같은 테이블에 서로 다른 별칭을 붙여 두 개의 테이블처럼 사용한다.

예를 들어 `film_actor`라는 하나의 테이블을 다음처럼 나눌 수 있다.

```sql
FROM film_actor a
JOIN film_actor b
```

여기서 `a`와 `b`는 모두 같은 `film_actor` 테이블이다.

즉,

```text
film_actor
   ↓
 ┌───┴───┐
 a       b
```

처럼 생각하면 된다.

## 언제 사용할까?

같은 테이블 안의 데이터끼리 관계를 비교해야 할 때 사용할 수 있다.

수업에서는 다음과 같은 상황을 다뤘다.

- 같은 영화에 출연한 배우 찾기
- 댓글과 대댓글 관계
- 조직도나 계층 구조
- 같은 그룹 내부 데이터 비교

---

## 🎬 같은 영화에 출연한 배우

```sql
SELECT
    a.actor_id AS actor_1,
    b.actor_id AS actor_2,
    a.film_id
FROM film_actor a
JOIN film_actor b ON a.film_id = b.film_id
WHERE a.actor_id < b.actor_id;
```

핵심은 다음 조건이다.

```sql
a.film_id = b.film_id
```

→ 같은 영화에 출연한 배우끼리 연결한다.

그런데 그대로 JOIN하면 같은 배우끼리 연결되거나 순서만 다른 중복이 생길 수 있다.

예:

```text
(1, 1)
(1, 2)
(2, 1)
(2, 2)
```

그래서 다음 조건을 사용한다.

```sql
WHERE a.actor_id < b.actor_id
```

그러면

```text
(1, 2) → 남음
(2, 1) → 제거
(1, 1) → 제거
```

가 된다.

### 핵심

> 같은 그룹에 속한 데이터끼리 조합을 만들되, 자기 자신과의 조합과 순서만 다른 중복을 제거한 것이다.

# 2. 💬 댓글과 대댓글

댓글 테이블에서도 Self Join을 사용할 수 있다.

```sql
CREATE TABLE comments (
    id INT PRIMARY KEY,
    content TEXT,
    parent_id INT,
    FOREIGN KEY (parent_id) REFERENCES comments(id)
);
```

여기서 중요한 부분은 다음과 같다.

```sql
FOREIGN KEY (parent_id) REFERENCES comments(id)
```

`parent_id`가 다른 테이블이 아니라 **같은 comments 테이블의 id를 참조한다.**

즉,

```text
id = 1
안녕하세요
parent_id = NULL
      ↓
id = 3
네 안녕하세요!
parent_id = 1
```

처럼 댓글과 대댓글 관계를 표현할 수 있다.

---

## 원댓글

원댓글은 부모 댓글이 없다.

```sql
WHERE parent.parent_id IS NULL
```

따라서 `parent_id = NULL`인 행이 원댓글이다.

---

## 댓글 + 대댓글 조회

```sql
SELECT
    parent.id AS parent_id,
    parent.content AS parent_content,
    child.id AS reply_id,
    child.content AS reply_content
FROM comments parent
LEFT JOIN comments child ON child.parent_id = parent.id
WHERE parent.parent_id IS NULL;
```

여기서는 같은 comments 테이블을 다음처럼 역할별로 나눈다.

```text
comments parent → 원댓글 역할
comments child  → 대댓글 역할
```

JOIN 조건은 다음과 같다.

```sql
child.parent_id = parent.id
```

예를 들어

```text
원댓글 id = 1
대댓글 parent_id = 1
```

이면 서로 연결된다.

### 왜 LEFT JOIN일까?

```sql
LEFT JOIN comments child
```

을 사용했기 때문에 대댓글이 없는 원댓글도 결과에 남는다.

대댓글이 없다면 다음 값이 `NULL`이 된다.

```text
reply_id      = NULL
reply_content = NULL
```

### 주의

이 쿼리는 **원댓글 바로 아래의 대댓글까지만 조회한다.**

대댓글 → 대대댓글처럼 더 깊은 단계까지 자동으로 조회하는 것은 아니다.

# 3. 👁️ View

## 무엇인가?

View는 **저장된 SELECT 쿼리를 테이블처럼 사용할 수 있게 만든 데이터베이스 객체**이다.

예를 들어 자주 사용하는 쿼리가 있다고 하자.

```sql
SELECT customer_id, activebool
FROM customer;
```

이를 View로 저장하면 다음처럼 사용할 수 있다.

```sql
CREATE VIEW customer_status AS
SELECT customer_id, activebool
FROM customer;
```

이후에는

```sql
SELECT *
FROM customer_status;
```

처럼 테이블을 조회하듯 사용할 수 있다.

---

## 중요한 특징

일반적인 View는 SELECT 결과 데이터를 따로 복사해서 저장하는 것이 아니다.

```text
View
 ↓
저장된 SELECT
 ↓
원본 테이블 조회
 ↓
결과 반환
```

따라서 원본 데이터가 바뀌면 View를 조회한 결과에도 반영된다.

---

## 왜 사용할까?

### 1) 복잡한 쿼리 단순화

매번 여러 테이블을 JOIN하지 않고 미리 View를 만들어둘 수 있다.

```sql
CREATE VIEW film_with_category AS
SELECT
    film.title,
    category.name AS category_name
FROM film
JOIN film_category
    ON film.film_id = film_category.film_id
JOIN category
    ON category.category_id = film_category.category_id;
```

이후에는 다음처럼 사용할 수 있다.

```sql
SELECT title
FROM film_with_category
WHERE category_name = 'Action';
```

즉,

```text
긴 JOIN 쿼리
    ↓
View로 저장
    ↓
간단한 SELECT
```

가 된다.

---

### 2) 필요한 정보만 제공

예를 들어 고객 테이블에 다음과 같은 정보가 있다고 하자.

```text
customer_id
이름
이메일
활성 여부
```

이름과 이메일을 보여주고 싶지 않다면 필요한 컬럼만 View로 제공할 수 있다.

```sql
CREATE VIEW customer_status AS
SELECT customer_id, activebool
FROM customer;
```

---

## View 생성

```sql
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;
```

## View 삭제

```sql
DROP VIEW view_name;
```

View를 삭제해도 원본 테이블의 데이터에는 영향을 주지 않는다.

---

# 4. 📦 Subquery

## 무엇인가?

Subquery는 **SQL문 안에 들어가는 또 다른 SELECT 쿼리**이다.

보통 괄호 안에 작성한다.

```sql
SELECT ...
FROM ...
WHERE 값 > (
    SELECT ...
);
```

쉽게 생각하면

> 안쪽 쿼리를 먼저 계산하고, 그 결과를 바깥 쿼리가 사용하는 구조

이다.

---

# 4-1. WHERE에서 하나의 값 사용

전체 도시 평균보다 인구가 많은 도시를 찾는다.

먼저 전체 평균을 구하면

```sql
SELECT AVG(population)
FROM city;
```

하나의 평균값이 나온다.

이를 WHERE 조건 안에 넣는다.

```sql
SELECT name, population
FROM city
WHERE population > (
    SELECT AVG(population)
    FROM city
);
```

동작을 단순화하면 다음과 같다.

```text
SELECT AVG(population)
        ↓
   예: 500000
        ↓
population > 500000
```

즉, 평균값을 사람이 직접 계산해서 입력하지 않아도 된다.

---

# 4-2. SELECT에서 출력값으로 사용

```sql
SELECT
    name,
    population,
    (SELECT AVG(population) FROM city) AS avg_population
FROM city;
```

결과는 개념적으로 다음과 같다.

| 도시 | 인구 | 전체 평균 |
|---|---:|---:|
| A | 800000 | 500000 |
| B | 300000 | 500000 |
| C | 400000 | 500000 |

`avg_population`은 모든 행에서 같은 전체 평균값이다.

### 주의

이처럼 서브쿼리 결과를 하나의 값으로 사용하는 경우에는 일반적으로

```text
컬럼 1개
행 최대 1개
```

여야 한다.

---

# 4-3. IN — 여러 결과를 조건으로 사용

이번에는 서브쿼리 결과가 하나가 아니라 여러 개다.

```sql
SELECT countrycode
FROM city
WHERE population >= 5000000;
```

예를 들어 결과가

```text
USA
CHN
IND
```

라고 하면 다음 쿼리는

```sql
SELECT code, name
FROM country
WHERE code IN (
    SELECT countrycode
    FROM city
    WHERE population >= 5000000
);
```

사실상 다음처럼 동작한다.

```text
country.code가

USA
CHN
IND

중 하나인가?
```

즉, `IN`은 **서브쿼리에서 반환된 여러 값 중 하나에 포함되는지 검사할 때** 사용할 수 있다.

---

# 4-4. FROM — 하나의 테이블처럼 사용

인구가 가장 많은 도시 5개의 평균을 구한다.

```sql
SELECT AVG(population) AS avg_population
FROM (
    SELECT name, population
    FROM city
    ORDER BY population DESC, id
    LIMIT 5
) AS top_cities;
```

처리 순서를 나누면 쉽다.

### 1단계

```sql
SELECT name, population
FROM city
ORDER BY population DESC, id
LIMIT 5;
```

인구 상위 5개 도시를 뽑는다.

### 2단계

그 결과를

```text
top_cities
```

라는 임시 테이블처럼 사용한다.

### 3단계

```sql
SELECT AVG(population)
FROM top_cities;
```

와 같은 개념으로 평균을 구한다.

---

## 왜 바로 이렇게 하면 안 될까?

```sql
SELECT AVG(population)
FROM city
LIMIT 5;
```

이 쿼리는 먼저 전체 도시의 평균을 하나 구한 뒤 그 결과에 `LIMIT`을 적용한다.

따라서

> 상위 5개 도시를 먼저 고르고 → 그 도시들의 평균을 계산

하려면 FROM절 서브쿼리가 필요하다.

---

# 4-5. 상관 서브쿼리

일반적인 서브쿼리는 독립적으로 실행할 수 있지만, **상관 서브쿼리는 바깥 쿼리의 값을 참조한다.**

```sql
SELECT c.name, c.countrycode, c.population
FROM city AS c
WHERE c.population = (
    SELECT MAX(c2.population)
    FROM city AS c2
    WHERE c2.countrycode = c.countrycode
);
```

핵심은

```sql
c2.countrycode = c.countrycode
```

이다.

안쪽 쿼리의 `c2`가 바깥 쿼리의 `c`를 사용한다.

예를 들어 현재 바깥 행의 국가가 `KOR`라면 개념적으로

```sql
SELECT MAX(population)
FROM city
WHERE countrycode = 'KOR';
```

를 구하고 현재 도시 인구와 비교한다.

그 결과 각 국가에서 인구가 가장 많은 도시를 찾을 수 있다.

---

# 4-6. 서브쿼리 장단점

## 장점

- 복잡한 조회를 안쪽/바깥 쿼리로 나눌 수 있다.
- 조회 결과를 바로 조건으로 사용할 수 있다.
- 조회 결과를 임시 테이블처럼 사용할 수 있다.

## 주의점

- 중첩이 깊어지면 흐름을 이해하기 어려워진다.
- 상관 서브쿼리는 반복 조회가 발생하면 비용이 커질 수 있다.
- **서브쿼리가 항상 JOIN보다 느린 것은 아니다.**

실제 성능은

- 쿼리 구조
- 인덱스
- 데이터 양
- DB 실행 계획

등에 따라 달라진다.

---

# 5. 🔍 Index

## 무엇인가?

Index는 **테이블에서 데이터를 더 빠르게 찾기 위한 자료구조**이다.

수업에서는 B-tree 같은 자료구조를 사용한다고 배웠다.

쉽게 생각하면 책의 색인과 비슷하다.

```text
인덱스 없음
→ 책 처음부터 찾기

인덱스 있음
→ 색인에서 위치 확인 후 바로 이동
```

---

## 생성

```sql
CREATE INDEX index_name
ON table_name (column_name);
```

## 삭제

```sql
DROP INDEX index_name;
```

---

## PostgreSQL에서 자동 생성되는 경우

### PRIMARY KEY

```sql
PRIMARY KEY
```

를 지정하면 인덱스가 자동으로 생성된다.

### UNIQUE

```sql
UNIQUE
```

를 지정해도 인덱스가 자동으로 생성된다.

### FOREIGN KEY

주의할 점은 PostgreSQL에서는

```sql
FOREIGN KEY
```

를 만들었다고 해서 **참조하는 쪽의 외래키 컬럼에 인덱스가 자동 생성되지는 않는다.**

---

# 5-1. Index가 효과적인 경우

### WHERE에서 일부 데이터 자주 검색

```sql
WHERE email = ...
```

처럼 전체 데이터 중 일부만 자주 찾는 경우.

### JOIN 조건

```sql
ON orders.customer_id = customer.id
```

처럼 테이블 연결에 자주 사용되는 컬럼.

### ORDER BY / GROUP BY

정렬이나 그룹화에서도 경우에 따라 인덱스의 도움을 받을 수 있다.

---

# 5-2. 카디널리티

**Cardinality는 컬럼이 가지는 고유한 값의 수**이다.

### 높은 카디널리티

값의 종류가 많다.

```text
id
이메일
주민등록번호
```

### 낮은 카디널리티

값의 종류가 적다.

```text
성별
결제 여부
등급
```

일반적으로 카디널리티가 높은 컬럼이 인덱스에 유리할 수 있지만, 실제 효과는 데이터 분포와 조회 조건에 따라 달라진다.

---

# 5-3. Index의 단점

Index는 조회 성능만 좋아지는 것이 아니다.

데이터가 변경되면 인덱스도 함께 관리해야 한다.

```text
INSERT
UPDATE
DELETE
   ↓
테이블 변경
+
인덱스 변경
```

따라서

- 데이터 입력/수정/삭제 비용 증가
- 추가 저장 공간 필요

라는 단점이 있다.

### 비효율적일 수 있는 경우

- 테이블 데이터가 매우 적음
- 조회보다 데이터 변경이 훨씬 많음
- 조건에 해당하는 행이 전체 데이터의 상당 부분임

---

# 6. 🔄 Transaction

## 무엇인가?

Transaction은 **여러 SQL 작업을 하나의 논리적인 작업 단위로 묶는 것**이다.

대표적인 예가 송금이다.

김철수가 이영희에게 30,000원을 송금한다면

```text
1. 김철수 -30,000
2. 이영희 +30,000
```

두 작업이 모두 성공해야 한다.

첫 번째만 성공하면

```text
김철수 돈은 빠짐
이영희 돈은 안 들어옴
```

이라는 문제가 생긴다.

따라서 두 UPDATE를 하나의 Transaction으로 묶는다.

---

# 6-1. 주요 명령어

| 명령어 | 의미 |
|---|---|
| `BEGIN` | 트랜잭션 시작 |
| `COMMIT` | 변경 확정 |
| `ROLLBACK` | 변경 취소 |

---

# 6-2. 송금 예시

```sql
BEGIN;

UPDATE transaction_account
SET balance = balance - 30000
WHERE account_id = 1;

UPDATE transaction_account
SET balance = balance + 30000
WHERE account_id = 2;

COMMIT;
```

처리 흐름은

```text
BEGIN
 ↓
출금
 ↓
입금
 ↓
모두 성공
 ↓
COMMIT
```

이다.

---

# 6-3. ROLLBACK

변경을 확정하지 않고 취소하려면

```sql
ROLLBACK;
```

을 사용한다.

```text
BEGIN
 ↓
UPDATE
 ↓
ROLLBACK
 ↓
UPDATE 취소
```

### 중요한 점

`COMMIT`이 완료된 변경은 그 뒤에 `ROLLBACK`한다고 해서 취소되지 않는다.

---

# 6-4. 오류가 발생한 경우

한 트랜잭션 안에서

```text
UPDATE 1 성공
UPDATE 2 실패
```

가 발생했다면 전체 작업을 취소해야 한다.

```sql
ROLLBACK;
```

을 실행하면 먼저 성공했던 변경도 취소할 수 있다.

---

# 6-5. Python 백엔드에서의 처리

```python
cursor = connection.cursor()

try:
    cursor.execute("BEGIN")

    cursor.execute("""
        UPDATE transaction_account
        SET balance = balance - 30000
        WHERE account_id = 1
    """)

    cursor.execute("""
        UPDATE transaction_account
        SET balance = balance + 30000
        WHERE account_id = 2
    """)

    connection.commit()

except Exception:
    connection.rollback()
    raise

finally:
    cursor.close()
```

전체 구조를 단순화하면

```text
try
 ├─ 작업
 ├─ 작업
 └─ 성공 → COMMIT

except
 └─ 실패 → ROLLBACK
```

이다.

`raise`는 예외를 다시 전달하여 요청을 처리하는 쪽에서도 실패 사실을 알 수 있게 한다.

---

## Transaction 사용 시 주의

트랜잭션은 필요한 작업이 끝났다면 바로 종료해야 한다.

너무 오래 열어두면 데이터 잠금 때문에 다른 작업이 기다릴 수 있다.

# 7. 🗃️ Database Design

## 무엇인가?

데이터베이스 설계는 서비스 요구사항을 바탕으로

- 어떤 데이터를 저장할지
- 데이터를 어떻게 나눌지
- 데이터 사이에 어떤 관계가 있는지

를 결정하는 과정이다.

결과적으로

- 개체(Entity)
- 속성(Attribute)
- Key
- 관계(Relationship)

를 정하고 ERD로 표현한다.

---

# 8. 🔑 Key

## 후보키 Candidate Key

행을 **유일하게 구분할 수 있는 최소한의 컬럼 조합**이다.

후보키는 두 조건을 만족한다.

### 유일성

같은 키 값을 가진 행이 둘 이상 존재하지 않는다.

### 최소성

키를 구성하는 컬럼 중 하나라도 빼면 행을 유일하게 구분할 수 없다.

예를 들어 수강신청에서

```text
학생ID
```

만으로는 학생이 여러 강좌를 신청할 수 있기 때문에 한 행을 구분할 수 없다.

```text
강좌ID
```

도 여러 학생이 같은 강좌를 신청할 수 있기 때문에 부족하다.

하지만

```text
(학생ID, 강좌ID)
```

의 조합은 같은 학생이 같은 강좌에 한 번만 신청한다는 조건에서 한 행을 구분할 수 있다.

---

# 8-1. 기본키 Primary Key

후보키 중에서 **대표로 선택한 키**이다.

```text
PRIMARY KEY
```

는

- 중복 불가
- NULL 불가

이다.

---

# 8-2. 복합키 Composite Key

두 개 이상의 컬럼으로 구성된 키다.

예:

```text
(학생ID, 강좌ID)
```

학생ID 자체는 반복될 수 있다.

```text
학생ID = 1
학생ID = 1
```

강좌ID도 반복될 수 있다.

하지만 두 컬럼의 **전체 조합**은 중복될 수 없다.

---

# 8-3. 외래키 Foreign Key

외래키는 다른 테이블 또는 같은 테이블의 기본키나 고유 키를 참조하여 관계를 연결한다.

예:

```text
ENROLLMENT.student_id
        ↓
STUDENT.id
```

```text
ENROLLMENT.course_id
        ↓
COURSE.id
```

---

# 9. ✅ 데이터 무결성

데이터 무결성은 **데이터의 정확성과 일관성이 유지되는 성질**이다.

DB에 아무 값이나 저장되지 않도록 Key와 제약조건을 사용한다.

---

## 9-1. 개체 무결성

기본키는

```text
중복 X
NULL X
```

여야 한다.

`PRIMARY KEY`로 보장한다.

---

## 9-2. 참조 무결성

외래키에 들어가는 값은 참조 대상에 존재해야 한다.

예를 들어

```text
ENROLLMENT.student_id = 100
```

이라면 `STUDENT` 테이블에 `id = 100`인 학생이 있어야 한다.

이를 `FOREIGN KEY`가 보장한다.

---

## 9-3. 도메인 무결성

컬럼에는 정해진 타입과 허용 범위에 맞는 값만 저장해야 한다.

예:

```sql
balance INTEGER NOT NULL CHECK (balance >= 0)
```

잔액은

- 정수
- NULL 불가
- 0 이상

이라는 조건을 만족해야 한다.

이를

- 데이터 타입
- `CHECK`
- `NOT NULL`

등으로 보장한다.

---

# 10. 🧩 정규화 Normalization

## 무엇인가?

정규화는 **불필요한 데이터 중복과 이상 현상을 줄이기 위해 테이블을 나누는 과정**이다.

---

# 10-1. 중복 때문에 발생하는 이상 현상

수강신청을 하나의 테이블에 모두 저장한다고 하자.

| 학생명 | 학생연락처 | 강좌명 | 강사명 | 강사연락처 |
|---|---|---|---|---|
| 김민준 | 010-1111 | 파이썬 | 이지수 | 010-0000 |
| 김민준 | 010-1111 | SQL | 이지수 | 010-0000 |
| 이서연 | 010-2222 | 파이썬 | 이지수 | 010-0000 |

같은 정보가 여러 번 반복된다.

---

## 수정 이상

강사 연락처가 변경되었는데 한 행만 수정하면

```text
이지수 → 010-9999
이지수 → 010-0000
```

처럼 같은 사람의 정보가 서로 달라질 수 있다.

---

## 삽입 이상

새 강좌를 만들었지만 아직 신청한 학생이 없다면 수강신청 테이블 구조에서는 강좌 정보만 따로 저장하기 어려울 수 있다.

---

## 삭제 이상

SQL 강좌의 유일한 신청 기록을 삭제했는데 그 행에 강좌 정보까지 함께 있었다면 SQL 강좌 정보 자체가 사라질 수 있다.

---

# 11. 1NF — 제1정규형

핵심은

> 한 칸에는 하나의 값만 저장한다.

예를 들어

```text
강좌명 = "파이썬, SQL"
```

처럼 여러 값을 한 칸에 넣지 않고

```text
김민준 | 파이썬
김민준 | SQL
```

처럼 행을 나눈다.

수업에서 처음 제시한 수강신청 테이블은 이미 1NF를 만족한다.

---

# 12. 2NF — 제2정규형

2NF는

```text
1NF 만족
+
후보키의 일부만으로 결정되는 일반 속성 분리
```

이다.

수업 예제의 후보키는

```text
(학생명, 강좌명)
```

이다.

그런데

```text
학생명 → 학생연락처
```

이다.

즉, 학생연락처는 후보키 전체가 아니라 `학생명` 하나만 알아도 결정된다.

또한

```text
강좌명 → 강사명, 강사연락처
```

이다.

그래서 데이터를

```text
학생
강좌
수강신청
```

테이블로 분리한다.

---

## 2NF 이후

### STUDENT

```text
id
학생명
학생연락처
```

### COURSE

```text
id
강좌명
강사명
강사연락처
```

### ENROLLMENT

```text
id
학생ID
강좌ID
신청일
```

그리고

```text
학생ID → STUDENT.id
강좌ID → COURSE.id
```

로 연결한다.

같은 학생이 같은 강좌에 중복 신청하지 못하도록

```text
(student_id, course_id)
```

조합에 `UNIQUE`를 적용한다.

---

# 13. 3NF — 제3정규형

3NF는

```text
2NF 만족
+
일반 속성이 다른 일반 속성을 거쳐 결정되는 구조 분리
```

이다.

2NF 상태의 강좌 테이블에 다음 데이터가 있다고 하자.

```text
강좌
 ├─ 강좌명
 ├─ 강사명
 └─ 강사연락처
```

관계를 보면

```text
강좌 → 강사명 → 강사연락처
```

가 된다.

강사 연락처는 강좌 자체의 속성이라기보다 강사에게 속한 정보다.

그래서 강사 테이블을 별도로 만든다.

---

## 3NF 이후

### INSTRUCTOR

```text
id
강사명
강사연락처
```

### COURSE

```text
id
강좌명
강사ID
```

그리고

```text
COURSE.instructor_id
        ↓
INSTRUCTOR.id
```

로 연결한다.

이렇게 하면 강사의 연락처가 바뀌었을 때 강사 테이블의 한 행만 수정하면 된다.

---

# 14. ➡️ 함수적 종속

## 무엇인가?

A 값이 정해졌을 때 B 값이 하나로 결정된다면

```text
A → B
```

라고 표현한다.

예:

```text
학생명 → 학생연락처
```

학생명이 정해지면 해당 학생의 연락처가 정해진다는 의미다.

---

## 부분 함수적 종속

복합 후보키의 **일부만으로 일반 속성이 결정되는 관계**이다.

예:

```text
후보키 = (학생명, 강좌명)

학생명 → 학생연락처
```

학생연락처를 결정하는 데 강좌명은 필요 없다.

2NF에서 이런 구조를 분리한다.

---

## 이행적 함수적 종속

값이 중간 속성을 거쳐 결정되는 관계다.

```text
강좌
 ↓
강사
 ↓
강사연락처
```

즉,

```text
강좌 → 강사명 → 강사연락처
```

와 같은 구조다.

3NF에서 이런 구조를 분리한다.

---

# 15. ⚡ 반정규화 Denormalization

정규화와 반대로 **성능 등을 위해 의도적으로 일부 데이터를 중복 저장하는 것**이다.

예를 들어 강좌별 신청자 수를 매번

```sql
COUNT(...)
```

로 계산하지 않고

```text
course.student_count
```

처럼 따로 저장할 수도 있다.

장점:

```text
조회 간단
조회 속도 개선 가능
```

단점:

```text
신청 발생 → student_count 수정
취소 발생 → student_count 수정
```

처럼 관련 데이터를 항상 함께 갱신해야 한다.

### 기본 방향

> 먼저 정규화된 구조를 만들고, 실제 성능상 필요성이 확인되면 반정규화를 검토한다.

---

# 16. 🗺️ ERD 작성 순서

## 1단계. 요구사항 분석

먼저 서비스 규칙을 정한다.

예:

```text
학생은 여러 강좌를 신청할 수 있다.
같은 강좌에는 한 번만 신청할 수 있다.
```

사용자 흐름도 정리한다.

```text
회원가입
   ↓
강좌 검색
   ↓
수강 신청
```

---

## 2단계. 개체 도출

관리해야 할 대상을 찾는다.

예:

```text
학생
강좌
강사
수강신청
```

---

## 3단계. 관계 파악

예:

```text
학생 ─ 신청 ─ 강좌
강사 ─ 담당 ─ 강좌
```

관계를

```text
1:1
1:N
M:N
```

으로 구분한다.

---

## 4단계. M:N 관계 해결

학생 한 명은 여러 강좌를 신청할 수 있고, 한 강좌에는 여러 학생이 신청할 수 있다.

즉,

```text
STUDENT M:N COURSE
```

관계다.

M:N 관계는 중간에 연관 테이블을 둔다.

```text
STUDENT
    ↓
ENROLLMENT
    ↓
COURSE
```

---

# 17. 🎓 수강신청 ERD 구조

```text
STUDENT
- id PK
- student_name UK
- student_phone

      1
      │
      N

ENROLLMENT
- id PK
- student_id FK
- course_id FK
- enrollment_date

      N
      │
      1

COURSE
- id PK
- course_name UK
- instructor_id FK

      N
      │
      1

INSTRUCTOR
- id PK
- instructor_name UK
- instructor_phone
```

---

## 관계 정리

### 학생 → 수강신청

학생 한 명은 여러 수강신청 기록을 가질 수 있다.

```text
STUDENT 1:N ENROLLMENT
```

### 강좌 → 수강신청

강좌 하나에도 여러 학생이 신청할 수 있다.

```text
COURSE 1:N ENROLLMENT
```

따라서 학생과 강좌의 관계는 결과적으로

```text
STUDENT M:N COURSE
```

이고 `ENROLLMENT`가 이를 연결한다.

### 강사 → 강좌

한 강사는 여러 강좌를 담당할 수 있다.

각 강좌에는 담당 강사가 반드시 한 명 있다고 가정했다.

```text
INSTRUCTOR 1:N COURSE
```

---

# 18. 🔐 중복 신청 방지

수강신청 테이블의

```text
student_id
course_id
```

각각은 여러 번 등장할 수 있다.

예:

```text
학생 1 → 파이썬
학생 1 → SQL
학생 2 → 파이썬
```

하지만

```text
(student_id, course_id)
```

조합은 중복되면 안 된다.

따라서 복합 `UNIQUE` 제약조건을 사용한다.

```text
UNIQUE(student_id, course_id)
```

이렇게 하면 같은 학생이 같은 강좌를 두 번 신청하는 것을 막을 수 있다.

---

# ✅ 오늘 핵심 한 번에 정리

```text
Self Join
→ 같은 테이블 안의 데이터끼리 연결한다.

View
→ 자주 사용하는 SELECT 쿼리를 테이블처럼 사용한다.

Subquery
→ 안쪽 SELECT 결과를 바깥 SQL에서 사용한다.

Index
→ 검색 속도를 높이는 자료구조지만 변경 비용이 추가된다.

Transaction
→ 여러 DB 작업을 전부 성공하거나 전부 취소하도록 묶는다.

Primary Key
→ 한 행을 대표해서 식별한다.

Foreign Key
→ 테이블 사이의 관계를 연결한다.

정규화
→ 중복과 이상 현상을 줄이기 위해 테이블을 나눈다.

1NF
→ 한 칸에 하나의 값.

2NF
→ 복합 후보키 일부에만 의존하는 속성을 분리.

3NF
→ 다른 일반 속성을 거쳐 결정되는 속성을 분리.

함수적 종속
→ A가 정해지면 B가 결정되는 관계.

반정규화
→ 필요할 때 성능을 위해 일부 데이터를 의도적으로 중복한다.

ERD
→ 개체, 속성, Key, 관계를 시각적으로 표현한다.
```
