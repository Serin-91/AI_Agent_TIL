# 설계 변경 기록

구현 중 `submission-docs/design-draft.md`의 초안과 달라진 설계가 생기면 아래 형식으로 기록한다.
최종적으로 이 기록을 `submission-docs/design-final.md`의 초안 대비 변경사항에 반영한다.

---

### Phase / Step

Phase 3 ~ 24 이전 전반

### 기존 설계

design-draft.md 기준 Checkpointer는 이후 Phase(영속 저장)에서 교체될 것을 전제로 특정하지 않았음.

### 변경된 설계

`InMemorySaver`를 Phase 24(영속 Checkpointer 도입) 이전까지 그대로 사용한다.

### 변경 이유

세션 내 interrupt/resume 흐름 검증에는 충분하고, 영속 저장 요구사항은 별도 Phase로 분리되어 있어
그 전까지 조기 도입할 이유가 없다.

---

### Phase / Step

Phase 8

### 기존 설계

승인 전에는 `bank_data.json`이 전혀 변경되지 않는다고 가정.

### 변경된 설계

`requests` 배열은 `create_request()`로 검증 시작 시점(pending)부터 기록하고,
`update_request_status()`로 awaiting_approval/completed/cancelled/failed까지 갱신한다.
accounts/cards/bills/transactions/reissue 등 실제 업무 대상 데이터만 승인 전 불변으로 유지한다.

### 변경 이유

승인 대기 중 요청 추적(어떤 요청이 왜 실패/대기 중인지)이 필요했고, 메타데이터 기록과
실제 금융 데이터 불변 보장은 별개 문제이므로 분리했다.

### Phase / Step

Phase 10 (승인 전 수정)

### 기존 설계

승인/거절만 자연어로 해석.

### 변경된 설계

`ApprovalDecision`으로 approve/reject/modify 3가지를 분류하고, modify 시 검증 State를
비운 뒤 해당 업무의 validate_* 노드로 되돌아가 재검증·재승인을 받는다. 이전 승인은 재사용하지 않는다.

### 변경 이유

사용자가 승인 전 금액/대상을 바꾸는 자연스러운 발화를 지원하기 위함.

### Phase / Step

전체 분류기(TaskClassification 등)

### 기존 설계

명시하지 않음.

### 변경된 설계

모든 구조화 출력 LLM 호출에 `temperature=0`을 사용한다.

### 변경 이유

### Phase / Step

Phase 13 (조건부 이체)

### 기존 설계

승인 시점 스냅샷을 그대로 실행.

### 변경된 설계

승인 응답을 처리하기 직전 `validate_conditional_transfer()`를 다시 호출해 최신 잔액 기준
이체액을 재계산하고, 승인 당시 금액과 다르면 이전 승인을 재사용하지 않고 validate_conditional로
되돌아가 새 스냅샷으로 다시 승인을 받는다.

### 변경 이유

승인 대기 중 다른 거래로 잔액이 바뀔 수 있어, 스냅샷이 아닌 실행 직전 실제 데이터 기준으로만
이체액을 확정해야 안전하다.

### Phase / Step

Phase 14~15 (다계좌 이체)

### 기존 설계

목적지별 개별 검증/실패 허용 여부 미정.

### 변경된 설계

- 하나라도 검증에 실패하면 전체 요청을 실패시킨다(일부만 반영 금지).
- 동일한 destination_nickname이 여러 번 나오면 합산해서 하나의 목적지로 처리한다.
- 실행 직전 재검증에서 총액을 감당할 수 없으면 금액을 줄여 일부만 실행하지 않고 그대로 실패 처리한다.

### 변경 이유

부분 성공은 사용자가 의도하지 않은 상태(일부만 이체됨)를 만들 수 있어, 전체 성공/전체 실패만
허용하는 것이 가장 단순하고 안전하다.

Phase 9-3

### 기존 설계

별도 Phase로 독립적으로 추가할 수 있는 범위다.

### Phase / Step

Phase 18 (lost_then_reissue 복합 요청)

### 기존 설계

명시하지 않음.

### 변경된 설계

한 노드에서 interrupt를 두 번 걸지 않고, 기존 단일 업무 노드(check_card_info/validate_card_change,
check_reissue_info/validate_reissue, request_approval)를 그대로 재사용한다. task_type을
`card_lost` -> `card_reissue`로 전환(`start_ltr_lock`/`ltr_continue_to_reissue`)하며, 분실 정지와
재발급을 `card_lost`/`card_reissue` 두 개의 독립된 child request로 각각 기록한다.

### 변경 이유

동일 그래프 실행 안에서 interrupt를 중첩하면 재개 지점 추적이 복잡해진다. 기존 단일 업무 노드를
재사용하면 승인/거절/수정 처리 로직을 새로 만들 필요가 없고, 두 단계를 독립 request로 남기면
어느 단계가 실패/취소됐는지 추적하기도 쉽다.

### Phase / Step

multi_transfer 승인 전 수정 (Phase 10 연장)

### 기존 설계

명시하지 않음.

### 변경된 설계

다계좌 이체는 승인 전 수정 시 목적지 일부만 부분 수정하는 것은 지원하지 않고,

### 변경 이유

부분 수정 병합 규칙(기존 목적지 유지/추가/치환)을 명확히 정의하지 않은 상태에서 지원 범위를
넓히면 사용자가 의도하지 않은 목적지가 남을 위험이 있다.

### Phase / Step

Phase 0~18 안정화 점검 (Phase 19 진입 전)

### 기존 설계

- `parse_request()`가 분류 필드만 갱신하고, 이전 top-level 요청의 request_id/transfer/
  conditional/multi_transfer/rename/card_change/reissue/reissue_update/reissue_cancel/
  approval/result/error/composite_next/ltr_lock_result를 명시적으로 초기화하지 않음.
- 일부 validate_* 실패 시 State.error만 설정되고 result가 없어 main.py의
  `final_state["result"]` 출력이 KeyError 또는 이전 요청의 stale result를 보여줄 수 있었음.
- execute_instant_transfer/execute_account_rename/execute_conditional_transfer/
  execute_multi_transfer 호출에 try/except가 없어, 승인 후 실행 단계에서 ValueError/OSError가
  나면 그래프가 그대로 예외를 던지고 request가 awaiting_approval에 남았음.
- execute_conditional_transfer/execute_multi_transfer가 account_id로 계좌를 조회할 때
  owner_id로 다시 필터링하지 않았음(다른 실행 함수들과 일관성 없음).

### 변경된 설계

- `parse_request()`가 위 필드들을 매 top-level 요청마다 None으로 초기화해서 반환한다.
  parse_request는 START에서만 실행되고 interrupt resume은 이 노드를 다시 거치지 않으므로
  resume 중인 State에는 영향이 없다.
- `respond()`에서 `result`가 없고 `error`만 있으면 `error`를 `result`로 승격시켜 항상
  `result` 키가 채워지도록 정리했다.
- 위 4개 execute_* 호출을 `except (ValueError, OSError)`로 감싸고, 기존 카드/재발급 계열의
  `except ValueError`도 `except (ValueError, OSError)`로 넓혀 저장 실패(OSError)도 동일하게
  request.status="failed" 처리한다.
- execute_conditional_transfer/execute_multi_transfer의 계좌 조회를 owner_id로 필터링해
  실행 직전에도 owner 소유가 아닌 account_id면 실패하도록 보강했다.

### 변경 이유

같은 thread_id로 연속 요청을 주고받는 CLI 구조상 이전 업무의 잔여 State가 다음 요청에
새어 들어가면 안 되고, 실행 단계의 예외를 잡지 않으면 그래프가 죽거나 요청이 영구히
awaiting_approval로 남는다. 기능 추가 없이 Phase 0~18 안정성만 보강했다.

### Phase / Step

Phase 21. 일괄 청구서 납부

### 기존 설계

Phase 14 multi_transfer는 "총액이 잔액을 초과하면 전체 요청을 실패시킨다"는 전체
원자적 저장 정책을 사용한다. pay_all_bills를 설계할 때 이 정책을 그대로 재사용할지
검토했다.

### 변경된 설계

pay_all_bills는 multi_transfer와 다른 정책을 사용한다.

- **처리 단위**: multi_transfer는 모든 목적지를 메모리에서 준비한 뒤
  `save_bank_data()`를 한 번만 호출(전체 원자적 저장)하지만, pay_all_bills는
  `execute_batch_bill_payment()`가 납기일 빠른 순으로 bill 하나씩 처리하고 그때마다
  즉시 저장한다.
- **잔액 부족 처리**: multi_transfer는 총액이 잔액을 초과하면 승인 자체를 실패시키지만,
  pay_all_bills는 총액이 잔액보다 많아도 승인을 막지 않는다. 건별 처리 중 특정 bill의
  잔액이 부족하면 그 bill만 `status="failed", reason="insufficient_balance"`로 남기고
  unpaid를 유지한 채 다음 bill을 계속 처리한다.
- **저장 실패 처리**: bill 저장 중 `OSError`가 나면 해당 bill만
  `reason="save_error"`로 실패 처리하고 그 즉시 반복을 중단한다(`interrupted=True`).
  이미 저장에 성공한 이전 bill들은 rollback하지 않고 그대로 둔다. 아직 시도하지
  않은 이후 bill들은 `status="unprocessed"`로 기록한다.
- **request 상태 정책**: 정상적으로 전체 순회를 끝냈으면(일부 bill이 잔액 부족으로
  실패했더라도) `request.status="completed"`로 남기고 bill별 completed/failed 결과를
  result에 담는다. 저장 오류 등으로 실행 자체가 중단된 경우에만
  `request.status="failed"`로 남긴다(result에 이전 completed/현재 failed/이후
  unprocessed를 모두 포함). 승인 거절은 기존 패턴과 동일하게 `cancelled`.
- 승인 대상 bill 목록은 승인 시점(`validate_pay_all`)에 확정한 스냅샷
  (`state["pay_all_bills"]["bills"]`)만 사용하고, 승인 후 새로 생기는 미납 청구서는
  이번 batch에 포함하지 않는다.

### 변경 이유

일괄 납부는 "하나라도 안 되면 전부 취소"가 아니라 "낼 수 있는 건 내고, 안 되는 건
다음에"가 사용자에게 자연스러운 동작이다. multi_transfer의 전체 실패 정책을 그대로
쓰면 미납 청구서 5건 중 1건 때문에 나머지 4건까지 납부되지 않는 결과가 되어 요구사항과
맞지 않는다.

### Phase / Step

Phase 22. 이전 금융 요청 결과 조회(followup_status)

### 기존 설계

design-draft.md에는 "이전 요청 결과를 다시 묻는" 흐름이 없었다. requests 배열은
Phase 8부터 기록되고 있었지만 조회 전용 함수/노드가 없었다.

### 변경된 설계

- `functions.get_requests(owner_id, request_id=None, task_type=None)`을 추가해
  owner 소유 요청 기록만 최근순(`created_at` 내림차순)으로 조회한다.
- `task_type="followup_status"`를 새로 추가한다. LLM(`followup_category`)은
  "이체/별명변경/카드변경/재발급/청구서납부" 중 어떤 종류의 이전 업무를 묻는지만
  분류하고, 성공/실패 여부는 절대 LLM이 판단하지 않고 requests.status/result에서
  읽는다.
- 이전 요청 선택 정책(가장 안전한 순서): (1) 이번 대화의 직전 request_id가 있고
  업무 종류가 맞으면 우선 사용, (2) 아니면 관련 task_type의 최근 기록 조회,
  (3) 후보 1개면 바로 안내, (4) 여러 개인데 "아까/방금" 같은 recency_hint가 있으면
  최신 1건, (5) 그래도 불확실하면 clarification interrupt로 번호를 선택받는다
  (`ask_followup_selection`, 후보 밖 번호는 Python `_match_index()`가 걸러낸다).
- followup_status는 조회 전용이라 새 requests를 만들지 않는다. "직전 request_id"를
  기억하기 위해 State에 `context: Optional[dict]` 필드를 새로 추가했는데, 이 필드는
  기존 transient State(request_id/transfer/... 등)와 달리 **parse_request()가
  초기화하지 않는다** - 다음 top-level 요청까지 그대로 유지되어야 하는 "대화 맥락"이기
  때문이다. `respond()`가 매 요청 종료 시 `state["request_id"]`가 있으면(승인/거절/
  실패 무엇이든) `context["last_request_id"]`에 남긴다.
- `_format_followup()`은 result가 dict여도 task_type별로 핵심만 뽑아 보여준다.
  특히 `pay_all_bills`는 batch 자체의 completed와 bill별 completed/failed(예:
  insufficient_balance)를 혼동하지 않도록 별도로 정리한다.

### 변경 이유

"아까 이체 됐어?" 같은 질문에 답하려면 이번 turn에서 새로 뭔가를 검증/실행하는 게
아니라 과거 requests 기록을 그대로 읽어야 한다. 성공/실패를 LLM에게 판단시키면
사실과 다른 답을 지어낼 위험이 있으므로, "어떤 종류의 업무인지 분류"까지만 LLM에
맡기고 실제 결과는 항상 저장된 데이터에서 읽도록 분리했다. 또한 State 초기화 정책
(Phase 0~18 안정화)이 "매 top-level 요청마다 이전 상태를 지운다"였는데, followup_status가
필요로 하는 "직전 요청이 무엇인지"는 정반대로 다음 요청까지 살아있어야 해서, 이를
구분하기 위해 transient State와 별도로 `context` 필드를 도입했다.

### Phase / Step

Phase 23. 대화 맥락 기반 금융 대상 확인 + Phase 9-3 ambiguous 후보 선택

### 기존 설계

Phase 9-3에서 `resolve_account_candidates()`/`resolve_card_candidates()`/
`resolve_address_candidates()`가 found/not_found/ambiguous를 반환하도록 만들어
뒀지만, ambiguous는 각 `validate_*()` 함수가 그대로 `ValueError`를 던져 실패로
끝내고 있었다(Graph에서 후보를 보여주고 선택받는 흐름은 Phase 23으로 보류돼 있었다).
또한 "그 카드"/"그 계좌"처럼 대상 이름이 생략된 요청을 재사용할 방법이 없었다.

### 변경된 설계

**1) 대화 맥락(context) 재사용 - transient State와 명확히 분리**

- Phase 22에서 추가한 `context` 필드(top-level 요청 사이에도 유지되는 유일한 State)를
  재사용한다. `account_lookup`/`card_lookup`/`reissue_lookup`(조회 노드)이 실행될 때마다
  결과가 정확히 1건이면 `context["account_nickname"]`/`context["card_name"]`에 그 이름을
  남기고, 2건 이상(또는 0건)이면 즉시 `None`으로 지운다 - "가장 최근 조회가 애매해지면
  오래된 명확한 값도 더 이상 믿지 않는다"는 원칙이다.
- `parse_request()`는 분류 직후, 현재 요청에 해당 필드가 없을 때만 context 값으로
  보완한다: `source_nickname`(instant/conditional/multi_transfer), `target_nickname`
  (rename_account), `card_name`(card_lock/unlock/lost/card_reissue/reissue_update/
  reissue_cancel). **금액/입금 목적지/승인 의사는 절대 context로 채우지 않는다** -
  이체 목적지·청구서 대상까지는 범위를 넓히지 않는다(요구사항 그대로).
- **범위상 명시적으로 제외한 것(디스클로저)**: `card_lost`처럼 카드 이름을 직접 지정해
  변경한 업무 자체는 context를 갱신하지 않는다(조회 노드만 갱신). 즉 "생활비 카드
  잃어버렸어, 정지해줘" 다음에 곧바로 "그 카드 재발급해줘"라고 하면 문맥이 아직 없어
  다시 물어본다(카드 조회를 한 번 거치면 그다음부터는 재사용된다). 이는 최소 침습을
  위한 의도적 축소이며, 필요하면 각 변경 업무의 승인 완료 시점에도 context를 갱신하도록
  나중에 확장할 수 있다.

**2) ambiguous 후보 선택(target_selection) - rename_account/card_lock·unlock·lost로 범위 한정**

- `resolve_rename_target()`/`resolve_card_target()`: 각각 `check_rename_info`/
  `check_card_info`의 "validate" 분기 직후에 끼워 넣은 새 노드. `resolve_account_
  candidates()`/`resolve_card_candidates()`로 ambiguous 여부만 먼저 확인하고,
  found/not_found는 그대로 `validate_rename`/`validate_card_change`에 맡긴다(기존
  동작 100% 유지). ambiguous일 때만 후보 목록을 `target_candidates`에 담아
  `ask_target_selection`으로 보낸다.
- `ask_target_selection()`: 후보를 번호로 보여주고(`interrupt(type="target_selection")`),
  응답이 후보 목록의 몇 번째인지는 **Python `_match_index()`가 숫자 검증만으로**
  판단한다(LLM에게 맡기지 않는다 - 후보 밖 대상을 LLM이 만들어내는 것을 원천 차단).
  후보 밖 입력이면 같은 목록으로 다시 질문한다.
  선택되면 `resolved_account_id`/`resolved_card_id`에 정확한 ID를 담아 원래
  검증 노드로 되돌아간다.
- `validate_account_nickname_by_id()`/`validate_card_status_change_by_id()`
  (functions.py 신규): `resolved_account_id`/`resolved_card_id`가 있으면 이름으로
  다시 찾지 않고 ID + owner_id로만 재검증한다(같은 이름의 다른 계좌/카드가 실수로
  선택되는 것을 방지).
- 카드 변경의 승인 전 수정(modify)에서 카드 이름이 바뀌면 `resolved_card_id`를 함께
  비워 다음 진입 때 `resolve_card_target`이 새 이름으로 다시 판단하게 한다(별명 변경
  modify는 계좌 자체를 바꾸지 않으므로 별도 처리 불필요).
- `main.py`에 `type == "target_selection"` 분기를 추가해 CLI가 정상적으로 번호
  입력을 받게 했다.
- **최초 범위 제외(이후 "Phase 23 마무리 보완"에서 연결 완료 - 아래 참고)**:
  최초 구현 시점에는 `card_reissue`/`reissue_update`/`reissue_cancel`의 카드 이름
  ambiguous와 배송지(주소) ambiguous를 target_selection으로 연결하지 않고
  `ValueError` 실패로 남겨뒀다. 8개 가까운 `validate_*` 호출부 전체에 동시에
  손대는 것을 피하기 위한 의도적 축소였다.

### 변경 이유

"확신할 수 없으면 질문, 임의 추측으로 금융 데이터 변경 금지"라는 절대 원칙을 지키려면
ambiguous 상태를 실패로 끝내지 않고 사용자에게 후보를 보여줘야 한다. 다만 모든
`validate_*` 호출부(이체 출금/입금, 조건부/다계좌 이체, 카드 4종, 재발급 3종, 청구서
2종)에 한 번에 이 흐름을 연결하는 것은 이번 Phase의 "대규모 리팩터링 금지" 원칙과
충돌한다. 그래서 최초 구현은 사용자가 지정한 최소 범위(계좌, 카드)에 한해 안전하게
완성하고, 나머지는 기존 동작(ValueError 실패)을 그대로 둔 채 범위를 문서에 명시적으로
남기는 쪽을 선택했다 - 조용히 다 됐다고 하기보다 무엇이 아직 안 됐는지 밝히는 편이
다음 작업자에게 더 안전하다.

### Phase / Step

Phase 23 마무리 보완. `card_reissue`/`reissue_update`/`reissue_cancel` ambiguous 후보 선택 연결

### 기존 설계

위 "Phase 23" 최초 구현에서 target_selection ambiguous 흐름은 `rename_account`(계좌)와
`card_lock`/`card_unlock`/`card_lost`(카드)에만 연결돼 있었고, 재발급 3종(`card_reissue`/
`reissue_update`/`reissue_cancel`)의 카드·배송지 ambiguous는 기존 `ValueError` 실패로
남아 있었다.

### 변경된 설계

기존 `resolve_rename_target`/`resolve_card_target` → `ask_target_selection` →
`resolved_account_id`/`resolved_card_id` 패턴을 그대로 재사용해 최소 확장했다(새 범용
프레임워크를 만들지 않음).

- **State 필드 추가**: `resolved_address_id`(배송지 ambiguous 선택 결과를 담는 필드,
  `resolved_account_id`/`resolved_card_id`와 동일한 성격의 transient State - 매
  top-level 요청마다 `parse_request()`가 초기화한다). `target_candidate_kind`에
  `"address"` 값을 추가했다(기존 `"account"`/`"card"`에 이어).
- **`resolve_reissue_target(state)`(신규)**: `card_reissue`/`reissue_update`가
  공유하는 검증 필드(`card_name` + `address_label`)의 ambiguous 여부를 순서대로
  확인한다. `resolved_card_id`가 아직 없으면 카드 이름 ambiguous를 먼저 확인하고,
  ambiguous면 그 후보만 반환해 `ask_target_selection`으로 보낸다. 카드가 이미
  확정됐거나 ambiguous가 아니면 이어서 `resolved_address_id`가 없을 때 배송지
  ambiguous를 확인한다. 두 확인 모두 통과하면(또는 애초에 ambiguous가 아니었으면)
  빈 dict를 반환해 `validate_reissue`/`validate_reissue_update`로 진행한다.
  선택 후 `ask_target_selection`이 다시 이 노드로 돌려보내므로(이미 확정된 항목은
  건너뜀), 카드·배송지 각각 최대 한 번씩만 선택을 요청하게 된다 - 한 노드에
  interrupt 두 개를 직접 두지 않고 기존처럼 단일 노드를 재사용하는 원칙(Phase 18)을
  그대로 따른다.
- **`resolve_reissue_cancel_target(state)`(신규)**: `reissue_cancel`은 카드만
  대상이므로 배송지 확인 없이 카드 이름 ambiguous만 확인한다.
- **`ask_target_selection()`**: `kind == "address"` 분기를 추가해 배송지 후보를
  번호/배송지ID/label/주소로 보여주고, 선택 결과를 `resolved_address_id`에 담는다.
  `route_target_selection()`도 `card_reissue`/`reissue_update` → `resolve_reissue_target`,
  `reissue_cancel` → `resolve_reissue_cancel_target`으로 되돌아가도록 분기를 추가했다
  (rename/card는 ambiguity가 하나뿐이라 기존처럼 validate로 바로 보낸다).
- **functions.py 신규 by-id 검증 함수**: `resolve_active_reissue_application_by_card_id`,
  `validate_reissue_request_by_ids`, `validate_reissue_address_change_by_ids`,
  `validate_reissue_cancellation_by_card_id`. 기존 이름/label 기반 함수와 동일한
  검증 규칙(카드 status==lost, 신청 status==requested, 중복 신청 금지 등)을 그대로
  따르되, 이름으로 다시 찾지 않고 `card_id`/`address_id`로 직접 조회한다 - 이렇게
  하지 않으면 "선택한 후보를 다시 문자열 이름으로 조회"할 때 또 ambiguous가 재발할
  수 있다.
- **`validate_reissue`/`validate_reissue_update`/`validate_reissue_cancel`**:
  `resolved_card_id`/`resolved_address_id`가 있으면 by-id 함수로, 없으면 기존
  이름/label 함수로 검증한다(`_resolved_card_id_or_lookup`/
  `_resolved_address_id_or_lookup` 헬퍼가 "확정된 ID 있으면 그대로, 없으면
  이름으로 조회하되 found가 아니면 실패"를 공통 처리).
- **승인 전 수정(modify)**: 세 재발급 승인 함수(`_request_reissue_approval`/
  `_request_reissue_update_approval`/`_request_reissue_cancel_approval`)의 modify
  분기에서 카드 이름/배송지 label이 바뀌면 `resolved_card_id`/`resolved_address_id`를
  함께 비운다(기존 카드 변경 modify와 동일한 패턴). `request_approval`의
  modify 라우팅도 `resolve_reissue_target`/`resolve_reissue_cancel_target`을
  거치도록 바꿔 rename/card와 일관되게 만들었다.
- `main.py`는 기존 `target_selection` 분기를 그대로 재사용하므로 수정하지 않았다.
- **비정상 fixture(같은 카드에 진행 중 신청이 2건 이상) 처리**: 정상 프로젝트
  규칙상 발생할 수 없으므로 새 선택 UI를 만들지 않고, by-id 검증 함수들이
  `resolve_active_reissue_application_by_card_id()`의 `ambiguous` 결과를 그대로
  `ValueError`로 방어적으로 실패시킨다(임의로 첫 번째 신청을 고르지 않는다).

이제 계좌 후보 선택 / 카드 후보 선택 / 재발급 관련 카드 후보 선택 / 배송지 후보
선택까지 모두 target_selection 흐름에 연결됐다.

### 변경 이유

card_reissue/reissue_update/reissue_cancel도 다른 계좌·카드 업무와 동일하게
"확신할 수 없으면 질문" 원칙을 지켜야 한다. 기존에 이미 검증된
`resolve_*_target`/`ask_target_selection`/`resolved_*_id` 패턴이 그대로 들어맞아서
새 구조 없이 최소 확장만으로 연결할 수 있었다.

## Phase 24: 프로그램 재시작 후 중단 업무 안전 복구

### 기존 설계

`InMemorySaver()`를 module import 시 바로 `graph_builder.compile()`에 넘겨
전역 `graph` 객체로 노출했다. checkpoint는 프로세스 메모리에만 존재해서
프로세스가 끝나면(정상 종료든 강제 종료든) 사라졌다. `main.py`는 매 실행마다
`uuid.uuid4()`로 새 `thread_id`를 만들었으므로, 애초에 재시작 후 이전
checkpoint를 다시 찾을 방법 자체가 없었다.

### 변경된 설계

- **checkpointer 교체**: `InMemorySaver` → `langgraph-checkpoint-sqlite`의
  `SqliteSaver`. 이 프로젝트는 단일 사용자·로컬·동기 CLI 데모라 별도 서버가
  필요한 Postgres 등은 과하고, 파일 하나로 끝나는 SQLite로 충분하다.
- **checkpoint 파일 위치**: `runtime/checkpoints.sqlite`(프로젝트 루트 기준).
  `bank_data.json`(금융 업무 데이터)과 책임이 다른 런타임 파일이라 완전히
  분리된 경로에 두고, `.gitignore`에 `runtime/`을 추가해 Git에 커밋되지 않게
  했다.
- **graph 생성 구조**: 전역 `graph = graph_builder.compile(...)`를 없애고
  `graph.py`에 `open_graph(checkpoint_path=None)` context manager를 추가했다.
  `SqliteSaver.from_conn_string(path)`가 이미 context manager라서(설치된
  `langgraph-checkpoint-sqlite==3.1.1` 기준 API를 실제로 설치해 확인함) 그
  connection을 그대로 감싸 컴파일된 graph를 `yield`한다. `main.py`가
  `with open_graph(...) as graph:` 블록 안에서 전체 대화 루프를 돌기 때문에,
  CLI 프로세스가 살아있는 동안 SQLite connection이 유지되고 프로그램이
  끝나면(정상 종료 시) 자동으로 정리된다. `checkpoint_path` 인자(및
  `main.py`가 읽는 `CHECKPOINT_PATH` 환경변수)로 테스트가 임시 DB를 주입할 수
  있어, 테스트끼리 실제 runtime DB를 오염시키지 않는다.
- **thread_id 영속 정책**: `uuid.uuid4()` 대신 `f"financial-agent:{OWNER_ID}"`
  고정값을 사용한다. `OWNER_ID`가 `"user-001"`로 고정된 단일 사용자 데모라는
  현재 프로젝트 범위에 가장 단순하게 맞는 정책이다. owner가 늘어나면
  `financial-agent:{owner_id}`로 자연히 분리되지만, **같은 owner가 CLI를
  동시에 여러 개 띄우는 멀티세션은 현재 지원 범위 밖**이다(같은 thread_id를
  공유하므로 동시 실행 시 checkpoint 경쟁이 생길 수 있음 - 이 프로젝트
  요구사항에는 없는 시나리오라 별도 처리를 추가하지 않았다).
- **checkpoint와 requests의 역할 차이**: `bank_data.json`의 `requests`는
  "업무 처리 기록/status"(pending/awaiting_approval/completed/cancelled/failed)
  이고, SQLite checkpoint는 "Graph가 어디서 중단됐고 어떤 State였는지"다. 이
  둘은 서로 다른 파일에 있고 서로를 갱신하지 않지만, 재시작 복구 시
  `checkpoint.values["request_id"]`와 `requests`의 동일 `request_id`를
  대조해 일관성을 확인한다.
- **재시작 시 중단 상태 감지**: `main.py`가 시작할 때마다
  `graph.get_state(config)`를 호출한다. `snapshot.next`가 비어 있으면(END
  상태) 중단된 실행이 없는 것이므로 곧바로 기존 새 입력 루프로 진입한다.
  비어 있지 않으면 `snapshot.tasks[0].interrupts[0].value`로 마지막
  interrupt payload(clarification/approval/target_selection - 기존 타입을
  그대로 재사용)를 복구해 사용자에게 다시 보여준다.
- **재시작 후 자동 승인 절대 금지(핵심 안전 규칙)**: `approval` 타입
  interrupt를 복구할 때, 재시작 전 사용자의 과거 입력을 어떤 형태로도 자동
  재생하지 않는다. 승인 요약을 다시 보여주고 **반드시 새 `input()`을 받아서만**
  `Command(resume=...)`를 호출한다. clarification/target_selection도 같은
  원칙으로 새 입력을 받는다.
- **requests와 checkpoint 불일치 시 안전 처리**: `approval` 복구 시
  `get_requests(owner_id, request_id=snapshot.values["request_id"])`로 조회해
  상태가 `awaiting_approval`이 아니면(이미 completed/cancelled/failed로
  종료된 경우) "이미 'X' 상태로 종료되었습니다. 다시 실행하지 않습니다."라고
  안내만 하고 **resume을 호출하지 않는다** - 곧바로 새 요청 입력 루프로
  넘어간다. clarification처럼 애초에 `request_id`가 없는 interrupt는 정상
  상황(아직 검증 전이라 request가 생성되지 않음)이므로 오류로 취급하지 않는다.
- **완료된 업무 재실행 금지**: 승인이 완료돼 `snapshot.next`가 빈 튜플이
  되면(그래프가 END까지 진행) 재시작 시 복구 로직 자체를 건너뛴다. 실제로
  실측(아래 테스트 참고)해 보면, 완료된 checkpoint 위에 새 `request` 입력으로
  `graph.invoke()`를 호출해도 LangGraph가 START부터 새로 시작하므로 과거
  interrupt가 다시 resume되는 일은 구조적으로 발생하지 않는다.

### 실제 프로세스 재시작 테스트

한 Python 프로세스 안에서 graph만 다시 만드는 것이 아니라, `subprocess`로
완전히 분리된 두 OS 프로세스(Process 1 → 종료 → Process 2)를 실행해 검증했다.
Process 1은 승인/clarification/target_selection 질문이 나온 직후 stdin을
닫아(EOFError) 실제 프로세스 강제 종료를 재현했다.

- **Test A(승인 대기 복구)**: P1에서 "생활비→저축 10만원" 승인 대기 중 종료,
  잔액 불변 확인. P2에서 같은 SQLite DB로 재시작 → interrupt 복구 → 새로
  "응, 진행해." 입력 → 정확히 1회 100,000원 이체, request completed. PASS.
- **Test B(재시작 후 거절)**: P1 승인 대기 후 종료, P2에서 "하지 마." →
  request cancelled, 잔액 불변. PASS.
- **Test C(clarification 복구)**: P1에서 "저축으로 10만원 보내줘." →
  "어느 계좌에서 출금할까요?" 상태로 종료. P2에서 질문이 그대로 다시 표시되고
  "생활비에서" → 검증 → approval interrupt까지 정상 진행. PASS.
- **Test D(target_selection 복구)**: synthetic fixture(동일 이름 카드 2개,
  `initial_data.json`은 수정하지 않고 `bank_data.json`만 테스트 중 임시
  수정)로 ambiguous를 만들어 P1에서 후보 선택 대기 중 종료. P2에서 동일
  후보 목록이 복구되고 번호 선택 → 선택된 카드에만 승인·잠금 적용,
  다른 카드는 불변. PASS.
- **Test E(completed 재실행 방지)**: P1에서 승인까지 완료(정상 종료, exit
  code 0). P2를 재시작해도 "재시작되었습니다" 복구 안내 자체가 뜨지 않고
  곧바로 새 입력 루프로 진입 - 잔액이 다시 바뀌지 않고 거래가 중복 추가되지
  않음을 확인. PASS.
- **Test F(requests/checkpoint 상태 불일치)**: P1에서 승인 대기 중 종료 후,
  fixture로 `requests`의 해당 항목 상태를 `completed`로 강제 변조(비정상
  상황 재현). P2가 이 불일치를 감지해 "이미 'completed' 상태로 종료되었습니다.
  다시 실행하지 않습니다."라고만 안내하고 승인 재확인도, 실행도 하지 않음을
  확인. PASS.
- **기존 기능 회귀**: 한 프로세스 안에서 카드 조회→"그 카드 잠가줘"(context
  재사용, ambiguous 아님)→승인→followup_status("아까 카드 잠금이 됐어?")→
  instant_transfer 승인→followup_status→card_lost까지 이어지는 연속 대화를
  실제로 실행해 전부 정상 동작함을 확인. PASS.

모든 테스트는 실제 `graph.invoke()`(Gemini API 실호출, `GEMINI_API_KEY`를
`langchain-google-genai`가 자동 인식)로 수행했고, 테스트마다 임시 SQLite DB
경로를 `CHECKPOINT_PATH` 환경변수로 주입해 실제 runtime DB를 건드리지 않았다.
모든 테스트 종료 후 `reset_bank_data()`로 `bank_data.json == initial_data.json`
을 재확인했다.

### 변경 이유

InMemorySaver는 프로세스가 살아있는 동안만 안전하고, 재시작 시나리오에서는
"승인 대기 중이던 이체가 통째로 사라지는" 정도가 최선이라 안전하긴 하지만
실용적이지 않다. 반면 checkpoint를 영속화하면 재시작 후 그 상태를 그대로
복구할 수 있는 대신, 잘못 다루면 "과거 승인 의사를 자동 재생해 중복 실행"하는
훨씬 위험한 실패 모드가 생긴다. 그래서 이번 Phase의 핵심은 저장 기술 교체
자체보다 "복구는 하되 실행 권한은 항상 새로 받는다"는 안전 규칙을 지키는
것이었다.

### Phase / Step

Phase 26 — 전체 실패/경계 시나리오 검증

### 기존 설계

`main.py`의 `_recover_interrupted_session()`은 재시작 시 approval interrupt를
복구할 때, checkpoint의 `request_id`로 `bank_data.json`의 `requests` 기록을
조회해 `status != "awaiting_approval"`인 경우(completed/cancelled/failed로
이미 종료된 경우)만 자동 재실행을 차단했다.

```python
if request_id:
    matches = get_requests(OWNER_ID, request_id=request_id)
    if matches and matches[0]["status"] != "awaiting_approval":
        ...  # 차단
```

### 발견한 안전 버그

`matches`가 빈 리스트(=해당 request_id 기록이 `requests` 배열에 아예 없음)인
경우 `matches and ...`가 그대로 거짓이 되어 차단 분기를 통과해버렸다. 즉
checkpoint에는 `request_id`가 남아 있는데 그 기록 자체가 사라진 상태
(fixture로 재현: 승인 대기 중 종료 → `requests`에서 해당 항목 삭제 → 재시작)
에서 사용자가 다시 "승인"을 입력하면, 그대로 `request_approval` 노드가 재개돼
`execute_instant_transfer()`가 실제로 실행되어 잔액/거래가 변경된 뒤에야
`update_request_status()`가 사라진 request_id를 찾지 못해 `ValueError`로
크래시했다. 즉 **금융 변경이 먼저 일어나고 그 다음에 프로그램이 죽는** 순서라
사용자는 크래시 메시지만 보고 실제로는 돈이 이미 이체된 상태를 알아채기 어렵다.
실제 별도 프로세스 2개로 재현해 100,000원이 이체됨을 확인했다.

### 변경된 설계

기록이 아예 없는 경우와 상태가 다른 경우를 분리해 둘 다 차단하도록 수정했다.

```python
if request_id:
    matches = get_requests(OWNER_ID, request_id=request_id)
    if not matches:
        print("이 요청에 대한 기록을 찾을 수 없어 상태가 일치하지 않습니다. "
              "다시 실행하지 않습니다.")
        return
    if matches[0]["status"] != "awaiting_approval":
        ...  # 기존 차단 로직 유지
```

### 변경 이유

Phase 24가 세운 안전 원칙("approval checkpoint 복구 + request_id 존재 + 해당
requests 기록 없음 → resume 금지 → 금융 실행 금지")을 실제로 지키지 못하는
구멍이었다. 재현 → 원인 특정 → 최소 수정(2줄 조건 분기 추가) → 동일 fixture로
재검증(별도 프로세스, `input()` 자체가 호출되지 않고 즉시 반환됨을 확인) →
기존 정상 케이스(정상 재시작+승인 1회 실행, 상태 불일치 차단) 회귀 확인까지
마쳤다. `src/main.py` 한 파일, 6줄 추가 외 다른 변경은 없다.

### Phase / Step

Phase 27 — 전체 End-to-End 회귀 테스트 (Scenario K)

### 기존 설계

Phase 23에서 `TaskClassification.source_nickname`/`destination_nickname`
필드 설명은 "'계좌', '통장' 같은 접미사는 빼고 순수 별명만 추출한다"까지만
규정했다. "그 계좌"처럼 실제 별명이 없는 지시어 표현을 만났을 때 이를
어떻게 다뤄야 하는지는 명시하지 않았다.

### 발견한 버그

Phase 23에서 실행 재현을 확실히 하지 못했던 "그 계좌에서 저축으로 10만원
보내줘" 시나리오를 Phase 27에서 실제로 `graph.invoke()`로 실행해 보니,
`_classifier`가 "그 계좌"라는 지시어 표현 자체를 `source_nickname`에
문자 그대로("그 계좌") 채워 넣었다. 그 결과:

- `_missing_transfer_fields()`가 `source_nickname`이 채워져 있다고 보고
  clarification을 건너뜀
- Phase 23이 만든 context 보완 로직(`if not source_nickname: source_nickname
  = context.get("account_nickname")`)도 `source_nickname`이 이미 값을
  가지고 있어 실행되지 않음
- 결국 `validate_transfer`가 "그 계좌"라는 존재하지 않는 계좌 이름으로
  검증을 시도해 사용자에게 혼란스러운 실패로 끝남(정상적인 "어느 계좌에서
  출금할까요?" clarification도 아니고, context가 의도한 대상 해석도 아님)

즉 지시어 표현이 있으면 Phase 23의 context 보완 메커니즘 자체가 무력화되는
버그였다. 이 프로젝트의 `account_lookup()`은 사용자가 특정 계좌 이름을
언급해도 항상 owner의 전체 계좌 목록을 반환하도록 설계되어 있어(카드/재발급
조회의 `card_name`/`address_label` 필터와 달리 계좌 조회에는 이름 필터가
없음), 이번 owner 픽스처(계좌 3개)로는 애초에 `context["account_nickname"]`가
특정 계좌 하나로 좁혀질 수 없다. 이는 별도의, 더 큰 범위의 설계 결정(계좌
조회에 이름 필터를 추가할지)이 필요한 사안이라 이번 회귀 테스트 범위에서는
건드리지 않았고, 아래 "남은 제한사항"에 기록만 한다.

### 변경된 설계

`source_nickname`/`destination_nickname` 필드 설명에 지시어 표현은 실제
별명이 아니므로 추출하지 말고 비워두라는 규칙을 추가했다.

```python
"'그 계좌', '아까 그 계좌', '거기서' 같은 지시어 표현은 실제 별명이 아니므로 "
"그대로 추출하지 말고 비워둔다(None) - 이후 대화 맥락으로 보완한다."
```

수정 후 같은 입력에서 `source_nickname`은 `None`으로 정상 처리되고, context도
비어 있으므로(위 제한사항 때문에) 정상적인 clarification("어느 계좌에서
출금할까요?")으로 안전하게 대체된다. Scenario A~H(계좌 조회, 승인 이체, 거절,
clarification, 승인 전 수정, 조건부 이체 재검증)를 수정 전후로 각각 실제
`graph.invoke()`로 재실행해 회귀가 없음을 확인했다.

### 변경 이유

지시어 표현을 실제 별명처럼 취급해 검증을 시도하는 것은 "확신할 수 없으면
질문한다"는 프로젝트 원칙(§15)에 위배되는 실제 분류 버그였다. `TaskClassification`
필드 설명 두 줄만 수정하는 최소 변경으로 고쳤고, 그래프 구조나 State 초기화
정책은 건드리지 않았다.

### 남은 제한사항 (의도적으로 이번에 고치지 않음)

`account_lookup()`은 여전히 특정 계좌 이름 언급과 무관하게 owner의 전체
계좌 목록을 반환한다(카드/재발급 조회와 달리 이름 필터가 없음). 따라서 현재
owner(계좌 3개) 데이터로는 "생활비 계좌 보여줘" → "그 계좌에서 ..." 같은
흐름에서 `context["account_nickname"]`가 "생활비" 하나로 좁혀지는 경우가
자연스럽게 발생하지 않는다. 이 문장 자체는 위 수정으로 더 이상 잘못된
계좌 이름으로 검증을 시도하지 않고 정상적인 clarification으로 안전하게
끝나지만, "context가 그 계좌를 정확히 기억해 곧바로 approval까지 가는"
Phase 23의 원래 시나리오를 owner_id="user-001"에서 완전히 재현하려면
`account_lookup`에 이름 필터를 추가하는 별도의 설계 결정이 필요하다. 이는
이번 회귀 테스트 범위를 넘는 기능 확장이라 손대지 않았다.

### Phase / Step

Phase 28 — Streamlit 데모 UI 추가 + 최종 제출 전 검증에서 발견한 안전 문제 수정

### 기존 설계

Phase 27까지는 CLI(`src/main.py`)가 유일한 실행 경로였고, 최종 검증 전까지
다음 네 가지가 실제 동작과 다르거나 방어가 비어 있는 상태였다.

1. `respond()`는 `lost_then_reissue` 복합 흐름에서
   `{"lock": ..., "reissue": state.get("result")}`만 만들었다. 재발급 단계가
   검증 실패로 끝나면 State에는 `result=None`, `error="..."`만 남으므로
   실패 사유가 `reissue: None`으로 사라졌다.
2. `find_transfer_accounts()`/`validate_multi_transfer()`가 대상 계좌를
   `{account["nickname"]: account for account in get_accounts(owner_id)}`
   딕셔너리로 찾았다. 같은 owner에게 같은 별명 계좌가 2개 이상이면 **뒤
   항목이 앞 항목을 조용히 덮어쓰고 그대로 승인 화면까지 진행**됐다.
   README/design-final/retrospective에는 "ambiguous면 실패로 처리된다"고
   적혀 있었으므로, 문서와 코드가 정반대였다.
3. `execute_bill_payment()`가 호출자에게 받은 `amount`를 현재
   `bill["amount"]`와 대조하지 않았다. 정상 graph 경로에서는
   `validate_bill_payment()`가 돌려준 금액만 넘기므로 재현되지 않지만,
   금융 실행 함수의 최종 방어선이 비어 있었다.
4. `lost_then_reissue`의 대상 카드가 동명 2개 이상일 때
   `route_ltr_start()`가 `"fail"`로 빠지면서 `"카드를 찾을 수 없습니다"`로
   안내했다. 카드가 2개나 있는데 없다고 말하는 잘못된 안내였다.

### 변경된 설계

**1) Streamlit 데모 UI (`app.py` 신규, `streamlit>=1.64.0` 의존성 추가)**

수업 발표에서 CLI 로그만으로는 "어디서 멈췄고 무엇을 검증했는지"가 잘
드러나지 않아, 같은 Agent를 브라우저에서 보여주는 얇은 wrapper를 추가했다.

- `app.py`는 `src/graph.py`의 `open_graph()`를 그대로 호출하고, 새로운
  분기/검증 로직을 만들지 않는다. 금융 판단은 전부 `src/`가 담당한다.
- interrupt `type`(approval/clarification/target_selection)에 따라 승인 버튼 /
  텍스트 입력 / 라디오 버튼 UI를 고른다. `Command(resume=...)`로 넘기는
  값은 CLI가 `input()`으로 받던 것과 같은 문자열이다.
- **demo checkpoint 분리**: CLI가 쓰는 `runtime/checkpoints.sqlite`를
  오염시키지 않도록 `runtime/demo_checkpoints.sqlite` + 별도 thread_id
  (`financial-agent-demo:{OWNER_ID}:{session_id}`)를 쓴다. "초기화" 버튼은
  연결 중인 SQLite 파일을 지우는 대신 새 `session_id`를 발급해 새 thread로
  옮겨가는 방식으로 대화를 리셋한다.
- `st.cache_resource`로 `open_graph()` context manager와 graph를 **함께**
  캐싱한다. graph만 반환하면 context manager가 참조를 잃고 GC되면서
  `__exit__`이 실행돼 SQLite connection이 즉시 닫힌다.

**2) `src/data_store.py` — Windows 파일 교체 재시도**

`save_bank_data()`의 `os.replace()`가 Windows에서 백신 실시간 검사 등이 방금
만든 임시 파일을 순간적으로 잠글 때 `PermissionError(WinError 5)`로 실패하는
경우가 있었다. 최대 5회, 0.1초씩 늘려가며 재시도하고 마지막에도 실패하면 기존대로
예외를 올린다. 임시 파일에 먼저 완전히 쓰고 교체하는 원래 안전 저장 구조는
그대로다(저장 실패 시 기존 `bank_data.json` 유지).

**3) `respond()` — 복합 흐름 실패 사유 보존 (`src/graph.py`)**

`ltr_lock_result`가 있을 때 재발급 결과가 `None`이고 `error`가 있으면 그
`error`를 재발급 결과 자리에 올린다. 정지 단계 결과는 그대로 보존하고, 단일
`card_reissue` 경로(문자열 결과)는 건드리지 않는다.

**4) 이체 계열 ambiguous 계좌 안전 처리 (`src/functions.py`)**

`find_transfer_accounts()`와 `validate_multi_transfer()`가 별명 딕셔너리 대신
기존 `resolve_account_candidates()`를 쓴다. `not_found`는 기존 메시지 그대로,
`ambiguous`는 `"계좌 별명이 여러 개와 일치합니다: {nickname}"`로 실패시킨다.
`validate_conditional_transfer()`는 `find_transfer_accounts()`를 재사용하므로
자동으로 같은 정책이 적용된다. **새 target_selection Graph 흐름은 추가하지
않았다** — 복합 흐름까지 포함해 후보 선택을 연결하려면 Node/Edge 설계 변경이
필요해 이번 범위(안전 수정)에서 분리했다.

**5) `execute_bill_payment()` amount 일치 검증 (`src/functions.py`)**

실행 직전 재검증에 `if amount != bill["amount"]: raise ValueError(...)`를
추가했다. 전달받은 금액을 `bill["amount"]`로 조용히 덮어쓰지 **않는다** —
그렇게 하면 사용자가 승인한 금액과 다른 금액을 집행하게 되기 때문이다.
불일치는 실행 자체를 막고, 기존 status/balance 검증은 그대로 뒤에 둔다.

**6) `start_ltr_fail()` 안내 문구 구분 (`src/graph.py`)**

`resolve_card_candidates()` 결과가 `ambiguous`면 `"카드 이름이 여러 개와
일치합니다"`, 그 외(`not_found`)는 기존 `"카드를 찾을 수 없습니다"`로 안내한다.
Node/Edge는 추가하지 않았고, 복합 흐름의 target_selection 미지원은
design-final §14/§23과 README에 제한사항으로 남겼다.

**7) 문서 동기화**

- `README.md`: `app.py`를 프로젝트 구조/의존성에 추가, Streamlit 실행 방법 추가,
  동명 대상 처리를 "번호 선택 / 안전한 실패" 두 갈래로 정확히 기술.
- `submission-docs/design-final.md`: §9-2, §12, §14, §15, §20, §23 수정.
  "모든 모호한 대상은 target_selection으로 처리한다"는 단언을 제거하고
  두 갈래 표로 대체. 복합 흐름 실패 사유 보존과 bill amount 방어를 반영.
- `submission-docs/retrospective.md`: 남은 한계를 실제 동작에 맞게 고치고,
  "확인하지 않은 안전 속성을 문서에 단언하면 안 된다"는 배운 점을 추가.

### 검증

수정 전 실패하던 케이스가 수정 후 통과하는 것을 실제 실행으로 확인했다.

- 이미 `lost` + 진행 중 신청 존재 상태에서 "정지하고 재발급해줘"
  → `{"lock": {"skipped": True, ...}, "reissue": "이미 진행 중인 재발급 신청이 있습니다: 생활비 카드"}`
- 정지 승인 후 존재하지 않는 배송지("우리집") 입력
  → 정지 결과(`new_status: lost`)는 유지되고 `"배송지를 찾을 수 없습니다: 우리집"`이 함께 전달
- 동명 계좌 합성 fixture에서 즉시/조건부/다계좌 이체 모두 승인 화면에 진입하지
  않고 `"계좌 별명이 여러 개와 일치합니다: 생활비"`로 중단, 잔액·거래 불변
- `execute_bill_payment(..., amount=1)` / `amount=1000000` 직접 호출 모두
  `ValueError` + 잔액·거래·bill status 전부 불변 (정확한 금액이면 기존대로 납부)
- 동명 카드 fixture의 `lost_then_reissue` → `"카드 이름이 여러 개와 일치합니다"`,
  없는 카드 이름 → `"카드를 찾을 수 없습니다"`

회귀는 기존 시나리오를 그대로 다시 돌려 확인했다. 실제 Gemini E2E 26건(계좌/
총잔액/거래내역 필터/추가 질문/승인 전 수정/자연어 승인·거절/후속 결과 조회/
카드 잠금·분실/재발급/청구서 납부·재납부 거부) 전부 이전과 동일하게 통과했고,
stub 기반 흐름 검증(승인 전 실행 금지, 거절 불변, modify 재검증, transient State
초기화, 조건부 이체 잔액 변동 재승인, 다계좌 1회 저장, 일괄 납부 부분 실패/저장
실패, owner_id 격리, SQLite approval/clarification/target_selection 복구, 상태
불일치 차단)도 전부 통과했다.

### 변경 이유

3~6번은 전부 "임의로 추측하지 않는다 / 실패하면 이유를 안내한다 /
금융 판단은 실행 직전에 다시 확인한다"는 기존 원칙(`CLAUDE.md` §8·§15)이
특정 경로에서만 지켜지지 않던 구멍이었다. 특히 2번은 코드가 아니라 **문서가
실제 동작과 반대로 적혀 있었다**는 점이 더 위험했다 — 제공된 데이터로는
재현되지 않는 경로라 정상 실행만으로는 끝까지 드러나지 않았다. 1번은 발표용
설명 보조 도구라 기존 `src/` 구조를 전혀 바꾸지 않는 wrapper로만 붙였다.

## Phase 29: 최종 보완 — Streamlit 전체 기능 지원, 승인 화면 자연어 입력,
데모 세션 복구, 재발급 신청 조회 후보 선택

### Phase / Step

Phase 29 — 최종 제출 전 마지막 보완. 금융 검증/실행 로직(`src/functions.py`의
계좌·이체·카드·청구서 규칙)은 그대로 두고, Streamlit UI 사용성과 재발급 신청
조회 하나만 손봤다.

### 기존 설계

1. Streamlit 입력창 placeholder와 예시가 이체 하나뿐이라 카드/청구서/조회
   기능이 있다는 게 잘 드러나지 않았다.
2. 승인 화면에 승인/거절 버튼과 "수정 내용 입력" 텍스트칸이 있었는데, 이
   텍스트칸은 이미 내부적으로 `request_approval()`의 `ApprovalDecision`을
   그대로 타서 "취소할게"처럼 거절 의사를 넣어도 정상 동작했다 - 다만
   라벨이 "수정 전용"처럼 보여서 이 사실이 드러나지 않았다.
3. `app.py`의 `session_id`는 `st.session_state`에만 있어 Streamlit 서버
   자체를 재시작하면 새 UUID가 발급됐다. 같은 `runtime/demo_checkpoints.sqlite`
   파일을 다시 열어도 `thread_id`(`financial-agent-demo:{owner}:{session_id}`)가
   달라져 이전 승인 대기 interrupt를 찾지 못했다.
4. `reissue_lookup()`은 재발급 신청이 2건 이상이면 후보를 고르게 하지 않고
   전체 목록을 그대로 반환하고 끝났다. `financial-agent-mini-project.md`
   요구사항(신청 여러 건이면 후보를 보여주고 사용자가 선택)과 어긋났다.

### 변경된 설계

**1) Streamlit 기능 도움말 (`app.py`)**

사이드바에 범주별(계좌·이체/카드/청구서/대화 기능) 요청 예시 expander를
추가했다(`HELP_EXAMPLES`). 입력창 placeholder도 이체 하나만 강조하지 않게
바꿨다. 새 분기/검증 로직은 추가하지 않았다 - 순수 안내 텍스트다.

**2) 승인 화면 "자연어로 답변" (`app.py`)**

기존 "수정 내용 입력" 폼을 "💬 자연어로 답변" 폼으로 라벨만 바꿨다. 동작은
이전과 동일하게 `Command(resume=사용자입력)`을 그대로 넘기고, 승인/거절/수정
판단은 여전히 `request_approval()`의 `ApprovalDecision`(기존 `src/graph.py`
로직)이 담당한다. app.py에 새 판단 로직을 만들지 않는다는 원칙을 지키기
위해, 이미 그렇게 동작하던 입력칸을 정확한 이름으로 다시 붙인 것에 가깝다.
버튼 2개(승인/거절)는 그대로 유지했다.

**3) demo session_id 영속화 (`app.py`)**

`runtime/demo_session_id.txt`에 session_id를 저장한다. 최초 실행 시 새
UUID를 만들어 파일에 쓰고(`_write_new_session_id`), 이후 실행/서버 재시작
시 파일에서 같은 ID를 읽는다(`_load_or_create_session_id`). "테스트 데이터
초기화" 버튼은 `reset_bank_data()` 후 새 ID를 만들어 파일에도 다시 저장한다
(리셋 이후 재시작해도 리셋된 새 thread를 이어간다). `runtime/demo_checkpoints.sqlite`
파일 자체는 그대로 두고(기존 방침 유지), `runtime/`은 이미 `.gitignore`에
있어 별도 수정이 필요 없었다.

**4) 재발급 신청 조회 후보 선택 (`src/graph.py`)**

`followup_status`/`followup_candidates`/`ask_followup_selection`과 같은
패턴으로 `reissue_candidates` State 필드와 `ask_reissue_selection` Node를
추가했다. `reissue_lookup()`은 이제 0건이면 안내 문구, 1건이면 interrupt
없이 바로 반환, 2건 이상이면 `reissue_candidates`만 채우고 끝낸다.
`ask_reissue_selection`은 번호를 clarification 성격 interrupt로 받고,
선택 검증은 기존 `_match_index()`(순수 Python, LLM 미사용)를 그대로
재사용한다. 범위 밖 번호는 `route_reissue_selection`이 같은 Node로 되돌려
다시 묻는다. 조회 업무라 승인(approval) 절차는 붙이지 않았다 - 새로운
target_selection이나 범용 프레임워크를 만들지 않고 followup 패턴만
재사용했다.

## Phase 30: Streamlit 결과 출력을 사람이 읽을 문장/표로 정리

### Phase / Step

Phase 30 — 금융 로직/LangGraph 분기/승인 정책은 그대로 두고, `app.py`가
`src/graph.py`·`src/functions.py`의 result를 화면에 보여주는 방식만 바꿨다.

### 기존 설계

`_run_and_record()`가 `str(final_state.get("result", ""))`로 결과를 그대로
채팅창에 찍었다. `total_balance`는 숫자만, `account_lookup`/`card_lookup`/
`transaction_lookup`/`unpaid_bills`는 dict 리스트의 Python repr이, `pay_all_bills`/
`lost_then_reissue`는 중첩 dict의 repr이 그대로 노출됐다. 승인 summary도
`\n`으로만 구분된 평문이었고, target_selection 라디오 버튼은 후보 정보 없이
"1번"/"2번"만 보여줬다.

### 변경된 설계

**`app.py`에 `format_user_result(final_state)` 추가** — `task_type`과 `result`
(+ 필요한 경우 `remaining_amount`/`card_name` 등 관련 State 필드)를 받아
`(문장, 표|None)`을 반환한다. 20개 task_type을 전부 개별 분기로 처리했고,
각 분기는 `execute_*()`/`get_*()`가 실제로 돌려주는 dict/list 키를 그대로
읽어 문자열 서식(`_money()`로 천 단위 쉼표, `STATUS_LABELS`/`CARD_TYPE_LABELS`로
영문 status/card_type 한글화)만 입힌다. 새 금융 판단이나 LLM 호출은 없다.

- `error`가 있고 `result`가 문자열이면(ValueError 등 실제 실행 실패) `⚠️` 경고로,
  `error` 없이 `result`만 문자열이면(거절/취소) 평문으로 구분한다 - 둘 다
  이미 `src/graph.py`가 결정한 정보이고, 여기서는 그 구분만 그대로 반영한다.
- `pay_all_bills`/`lost_then_reissue`는 건별/단계별 결과를 ✅/❌/⏸ 기호를 붙인
  줄로 펼친다. `lost_then_reissue`는 정지 단계가 `{"skipped": True, ...}`면
  건너뛴 것으로, 그 외 dict면 성공으로, 문자열이면(거절/실패 메시지) 미완료로
  표시한다 - 이미 §7(implementation-changes 앞부분, Phase 28-1)에서 보존해둔
  실패 사유를 그대로 노출하는 것이지 새로 추측하지 않는다.
- `followup_status`는 `_format_followup()`이 이미 자연어 문장으로 정리한
  result를 그대로 통과시킨다(다시 가공하지 않음).
- 예상 못한 형태(dict/list인데 위 분기 어디에도 안 걸림)는 raw 노출 대신
  "요청이 처리되었습니다. (자세한 내용은 '🔧 상세 State 보기'에서 확인)"으로
  안내한다 - 원인을 추측해 지어내지 않는다.
- `_push()`/메시지 replay 루프에 `table` 필드를 추가해, 표가 필요한 결과(계좌/
  카드/거래내역/미납 청구서/재발급 신청 여러 건)는 `st.table()`로, 나머지는
  `st.markdown()`으로 렌더링한다.
- `_format_approval_summary()`: 기존 `summary`("key: value" 줄 + 마지막 질문 줄)를
  분해해 불릿 목록 + 굵은 질문으로 재구성한다(내용은 그대로, 표현만 변경).
- `_target_selection_labels()`: 라디오 버튼 각 항목에 후보의 핵심 정보(계좌
  잔액/카드 상태/배송지 주소)를 함께 보여준다. 선택값은 여전히 번호만
  추출해(`choice.split("번", 1)[0]`) 기존과 동일하게 resume한다.
- 하단 계좌/카드/청구서/최근 Request 탭도 같은 라벨 맵을 재사용해 raw status/
  card_type/task_type이 그대로 보이지 않게 정리했다.

### 검증

### 변경 이유

과제 심사·시연 화면에서 `{'source': {...}}` 같은 Python repr이 보이면 "실제
서비스처럼 자연스럽다"는 인상을 줄 수 없다. 반대로 이 formatter가 임의로
숫자를 재계산하거나 성공/실패를 추측하면 `src/`가 이미 검증한 결과와 화면
표시가 어긋나는 새로운 버그를 만들 위험이 있으므로, 전부 기존 result의
필드를 그대로 읽어 서식만 바꾸는 순수 표현 계층으로 한정했다.

## Phase 31: "새로고침하면 금융 데이터가 초기화된다" 조사 - 재현 결과 코드 결함 없음

### Phase / Step

Phase 31 — "이체 승인 → 브라우저 새로고침 → 잔액이 초기값으로 돌아간다"는

### 조사 방법과 실제 결과

1. **`reset_bank_data(` / `save_bank_data(` / `BANK_DATA_PATH` / `INITIAL_DATA_PATH`

### 결론 - 정확한 원인

**`app.py`/`data_store.py`/`functions.py`에는 자동으로 데이터를 초기화하는
코드가 없다.** `reset_bank_data()`는 여전히 버튼에서만 호출된다. 재현
결과가 보여주는 진짜 원인은: **Streamlit 서버가 실행 중인 동안 같은
`bank_data.json` 파일에 대해 `reset_bank_data()`(또는 동일 경로에 대한
직접 쓰기)를 호출하는 별도 프로세스가 있으면, 그 서버를 보고 있는 브라우저는
다음 새로고침에서 그 프로세스가 남긴 값을 그대로 보여준다**는 것이다.
`bank_data.json`은 여러 프로세스가 공유하는 단일 파일이고, 코드 어디에도
"이 파일은 지금 한 서버가 쓰고 있다"는 잠금/보호 장치가 없기 때문이다.

이번 조사 기간에는 이 프로젝트를 개발하면서 `reset_bank_data()`/
`git checkout -- data/bank_data.json`을 여러 번 실행했는데, 그때 이미
Streamlit 서버가 떠 있었다면 정확히 이 경로로 실제 화면에 영향을 줄 수
있었다. 왜 "새로고침 때만" 증상이 보였는지도 이걸로 설명된다 - 승인 직후
화면은 그 turn의 `st.rerun()`이 그 시점 값을 이미 그려서 보여주지만,
그 사이 파일이 다른 프로세스에 의해 바뀌면 다음 새로고침에서야 그 변경이
반영되어 보이기 때문이다.

### 변경 사항

코드 로직은 바꾸지 않았다(이미 올바르게 동작 중이었음을 확인했으므로).

1. **`src/data_store.py`**: `reset_bank_data()` docstring에 이 위험을

   동일 파일에 직접 쓰면 사용자 모르게 초기화된 것처럼 보인다"는 것을
   문서화해, 다음에 이 프로젝트를 개발/테스트할 때(이 프로젝트 자신을
   포함해) 같은 실수를 반복하지 않도록 했다.
2. **`src/test_real_disk_persistence.py`(신규)**: fake store로 우회하지
   않고 실제 `BANK_DATA_PATH`에 대해 `execute_instant_transfer()` →
   완전히 새로운 `load_bank_data()` 호출로 재확인 → 잔액/거래내역이 실제
   디스크에 남아 있는지 검증한다. 테스트 시작/종료 시 `reset_bank_data()`로

다른 변경 업무(조건부/다계좌 이체, 별명 변경, 카드 상태 변경, 재발급

영속된다"는 사실은 특정 업무 하나가 아니라 모든 변경 업무에 동일하게
적용된다(기존 `test_result_formatting.py`/`test_nickname_matching.py`가
이미 각 업무의 `execute_*()` 반환값 구조는 개별 검증해뒀다).

### 변경 이유

증상은 재현됐지만 재현 조건이 "이 코드베이스의 버그"가 아니라 "같은 파일을
공유하는 프로세스 두 개가 동시에 존재"였다. 존재하지 않는 버그를 코드에서
지어내 고치는 대신, 실제로 확인된 사실(호출 경로 감사 결과 + 실제 브라우저
재현 결과)만 보고하고, 앞으로 같은 혼동이 재발하지 않도록 문서화와
디스크 영속성 회귀 테스트만 추가했다.

## Phase 32: "새 대화 시작"과 "금융 데이터 초기화" 책임 분리

### Phase / Step

Phase 32 — 사이드바 버튼 하나(`_reset_conversation()`)가 대화 리셋과
`reset_bank_data()`를 함께 호출하던 것을 분리했다.

### 기존 설계

`_reset_conversation()` 하나가 `reset_bank_data()` + 새 session_id 발급 +
`messages`/`pre_accounts` 초기화를 전부 했다. 그래서 "대화만 새로 시작하고
싶다"는 요청이 불가능했다 - 버튼을 누르면 이체/카드 상태/청구서 납부 등
이미 승인 완료된 금융 데이터까지 항상 함께 초기화됐다.

### 변경된 설계

`app.py`에서 `_reset_conversation()`을 두 함수로 나눴다.

- `_start_new_conversation()`: 새 session_id 발급 + `demo_session_id.txt`
  갱신 + `messages`/`pre_accounts` 초기화만 한다. `reset_bank_data()`를
  호출하지 않는다.
- `_reset_financial_data()`: `reset_bank_data()` 호출 후
  `_start_new_conversation()`을 그대로 재사용한다. `app.py`에서
  `reset_bank_data()`를 호출하는 곳은 이 함수 한 곳뿐이다(Phase 31에서
  확인한 감사 결과와 동일한 불변조건을 유지).

사이드바도 버튼 2개로 나눴다: "🔄 새 대화 시작"(바로 실행)과
"🗑️ 테스트 금융 데이터 원상복구"(체크박스를 먼저 체크해야 버튼이
활성화되는 최소한의 확인 UI). 금융 로직/LangGraph 흐름/승인 정책은
전혀 건드리지 않았다.

### 검증

`src/test_conversation_reset_split.py`(신규, 실제 `bank_data.json`/
`demo_session_id.txt` 대상): 이체를 실제로 실행한 뒤 `_start_new_conversation()`을
호출해도 잔액이 그대로인지, `_reset_financial_data()`를 호출하면
`initial_data.json` 기준으로 정확히 되돌아가는지 확인했다. 두 테스트 모두
끝나면 `reset_bank_data()`로 정리한다. 기존 회귀 테스트(총 46개)도 다시
돌려 전부 통과했다(신규 2개 포함 48개, 0 FAIL).

### 변경 이유

Phase 31에서 확인했듯 `bank_data.json`은 대화 세션과 무관하게 유지돼야
하는 source of truth다. 그런데 유일한 초기화 버튼이 두 책임(대화 리셋 /
금융 데이터 리셋)을 항상 같이 수행하면, "대화창만 정리하고 싶다"는
일반적인 사용에서도 매번 실수로 금융 데이터를 날릴 위험이 있었다. 두
동작을 각자 다른 버튼으로 분리하고 파괴적인 쪽에만 확인 체크박스를 둬서
의도치 않은 초기화를 줄였다.
