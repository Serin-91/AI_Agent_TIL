# 금융 업무 AI Agent - 설계 초안

## 1. 설계 목표

사용자의 자연어 요청을 분석하여 금융 업무 유형을 분류하고,
필요한 정보를 확인한 뒤 조회 또는 변경 업무를 수행하는 AI Agent를 설계한다.

단순 조회 업무는 바로 실행할 수 있도록 하고,
실제 데이터가 변경되는 업무는 사용자 승인을 받은 뒤 실행하도록 구성한다.

---

## 2. 주요 업무 분류

초기 설계에서는 금융 업무를 다음 4가지 영역으로 구분하였다.

### ① 조회·계좌
- 계좌 목록 / 잔액
- 총잔액
- 거래내역
- 별명 변경

조회 업무는 바로 결과를 반환하고,
별명 변경과 같이 데이터가 변경되는 작업은 승인 절차를 거친다.

### ② 이체
- 즉시이체
- 조건부이체
- 다계좌이체

이체 업무에서는 계좌 잔액과 이체 금액 등
실행 가능 여부를 판단하기 위한 조건 검증이 필요하다.

### ③ 카드관리
- 카드 조회
- 분실정지
- 일시잠금 / 잠금해제
- 재발급 / 신청조회
- 수정 / 취소
- 정지 후 재발급

카드 상태를 변경하는 작업은 실제 데이터 변경이 발생하므로
사용자의 승인을 받은 뒤 실행하도록 설계한다.

### ④ 공과금·납부
- 미납 조회
- 단건 납부
- 일괄 납부

납부 작업에서는 잔액과 납부 상태 등을 확인한 뒤
실행 가능 여부를 판단한다.

---

## 3. 공통 처리 흐름

모든 요청은 먼저 사용자 자연어 요청을 분석하고 업무 유형을 분류한다.

이후 다음 흐름을 공통적으로 사용한다.

1. 필요한 정보가 충분한지 확인한다.
2. 정보가 부족하면 사용자에게 추가 질문을 한다.
3. 업무 수행에 필요한 조건을 검증한다.
4. 실행할 수 없는 경우 실패 이유를 안내하고 종료한다.
5. 실행 가능한 경우 데이터 변경 여부를 판단한다.
6. 조회 업무는 바로 실행한다.
7. 데이터 변경 업무는 사용자 승인을 요청한다.
8. 사용자가 거절하면 작업을 종료한다.
9. 사용자가 승인하면 실제 업무를 실행한다.
10. 실행 결과를 저장하고 사용자에게 안내한 뒤 종료한다.

---

## 4. Human-in-the-Loop 설계

금융 업무에서는 이체, 카드 상태 변경, 납부 등
실제 데이터가 변경되는 작업을 Agent가 바로 실행하지 않도록 설계하였다.

데이터 변경이 필요한 경우 사용자에게 실행 내용을 보여주고 승인을 요청한다.

- 승인 → 업무 실행
- 거절 → 실행하지 않고 종료

이를 통해 조회 업무와 변경 업무의 처리 방식을 분리하고,
중요한 작업에는 Human-in-the-Loop를 적용한다.

---

## 5. State 초안

Agent의 처리 과정에서 필요한 정보를 State에 저장하도록 설계하였다.

### 요청 정보
- `request`
- `task_type`

### 업무 대상
- `account`
- `card`
- `bill`
- `amount`
- 기타 업무 조건

### 처리 상태
- `approval`
- `status`

### 처리 결과
- `result`
- `error`

구현 과정에서 실제 노드 간에 전달해야 하는 정보가 확인되면
State 필드는 추가하거나 조정할 수 있다.

---

## 6. 공통 대화 처리

단일 요청 처리뿐 아니라 다음과 같은 대화 상황도 고려하였다.

- 업무 대상이 불명확한 경우 사용자에게 다시 확인
- 승인 직전에 사용자가 요청 내용을 수정하는 경우
- 자연어 승인 / 취소 표현 처리
- 이전 처리 결과를 이용한 후속 조회
- 재시작 및 장애 복구

---

## 7. 초기 설계에서 중요하게 본 기준

초기 설계에서는 다음 세 가지를 중심으로 구조를 구성하였다.

1. **조회와 데이터 변경 업무를 구분한다.**
2. **정보가 부족하면 임의로 실행하지 않고 사용자에게 추가 질문한다.**
3. **금융 데이터가 변경되는 작업은 사용자 승인 후 실행한다.**

이 문서는 구현 전 작성한 설계 초안이며,
실제 LangGraph 구현 과정에서 노드 구성, State 구조, 분기 조건 등이 변경될 수 있다.
변경된 내용과 이유는 최종 설계 문서에서 초안과 비교하여 정리한다.
